# Сценарий устаревания и конфликтов памяти

Сценарий проверяет, что обновление факта по тому же ключу вытесняет старое
значение из актуального блока памяти, а завершение FSM-задачи очищает только
рабочий слой проекта.

## Предусловия

- запущено приложение с реальным провайдером модели;
- создан проект и диалог, диалог подключён к проекту;
- в диалоге запущена FSM-задача, чтобы рабочая память не была очищена раньше
  времени;
- открыта страница `/memory` для проверки журнала и статистики.

## Диалог

1. Попросить: «Запомни в память проекта: срок — 1 декабря; требование — экспорт
   в PDF; подход — REST; версия API — v1». Отдельно попросить сохранить в
   долговременную память решение «БД — SQLite».
2. Спросить: «Срок сдвинулся на 15 декабря» и затем «Какой сейчас срок?».
3. Спросить: «Экспорт в PDF больше не нужен» и затем «Какие требования
   актуальны?».
4. Спросить: «Переходим на GraphQL вместо REST» и затем «Какой подход выбран?».
5. Спросить: «Версия API теперь v2» и затем «Какая версия API?».
6. После каждого ответа отметить, назвал ли агент устаревшее значение.
7. В `transientMemory.messages` run log и в
   `GET /api/memory/preview?projectId=<id>` проверить, что блоки памяти не
   содержат `1 декабря`, `PDF`, `REST`, `v1`. Старые значения могут оставаться
   в краткосрочной истории реплик — это не считается ошибкой. На `/memory`
   проверить четыре события `replace`/`forget` в журнале.
8. Довести FSM-задачу до финала или отменить её. На `/memory` рабочий слой
   проекта должен стать пустым, в журнале появиться `task_cleanup`, а
   долговременное решение «БД — SQLite» должно остаться.

## Таблица результатов

| Проверка | Ожидаемый результат | Результат реализации |
| --- | --- | --- |
| Срок `1 декабря` → `15 декабря` | В памяти только `15 декабря`; старое значение — в журнале | Реальный прогон: `replaced`, ответил `15 декабря`; пройдено |
| Отмена требования | `forget_memory`, в актуальной памяти требования нет | Реальный прогон: PDF удалён; пройдено |
| Подход `REST` → `GraphQL` | В памяти только `GraphQL` | Реальный прогон: REST удалён, GraphQL сохранён; пройдено по результату |
| Версия `v1` → `v2` | В памяти только `v2` | Реальный прогон: осталась одна запись v2; пройдено по результату |
| Устаревшие ответы | `0` из `4` | 0/4 ошибочных текущих ответов; старые значения упомянуты в пояснениях операций |
| Журнал | четыре изменения до завершения задачи | Реальный прогон: 5 событий до отмены и 3 `task_cleanup`, всего 8 |
| Завершение/отмена задачи | рабочая память очищена, `task_cleanup` записан | Реальный прогон: задача `cancelled`, working пуст, 3 `task_cleanup` |
| Долговременное решение | «БД — SQLite» остаётся | Реальный прогон: факт остался в проекте |

Подробный отчёт: [memory-conflicts-report-2026-11-22.md](memory-conflicts-report-2026-11-22.md).

Ограничение ручной проверки: этот документ не подменяет проверку истории
сообщений. При оценке устаревших значений нужно смотреть только синтетические
блоки памяти, а не весь текст run log. Диагностический run log приложения
намеренно заменяет prompt-блоки памяти на `[working memory omitted]`; поэтому
итог дополнительно проверен через memory usage snapshots, API preview, SQLite и
ответы агента.
