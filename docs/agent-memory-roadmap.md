# Развитие памяти агента

Дата: 2026-11-17. Статус: заметка для дальнейшего проектирования. Документ сохраняет идеи продвинутой версии; он не является утверждённым дизайном или планом реализации.

## Согласованная основа первой версии

Приложение получает три раздельных слоя памяти: краткосрочную память диалога, рабочую память задачи и долговременную память. Пользователь явно выбирает содержание и слой для сохраняемых записей. Модель фактов становится основой долговременного хранения.

Проект представляет одну задачу и объединяет несколько диалогов с общей рабочей памятью. В интерфейсе пользователь создаёт проект и ведёт диалоги внутри него. Отдельного уровня задач внутри проекта в первой версии нет.

Каждый слой получает собственное правило включения данных в промпт. Для первой версии выбран ручной способ сохранения и сборка контекста по явным правилам. Предложения модели и автоматический поиск подходящих фактов остаются за пределами первой версии.

Отдельная страница предназначена для управления памятью и просмотра статистики. Рабочие и долговременные записи можно просматривать, редактировать и удалять; каждый слой можно очищать. Краткосрочная память поддерживает просмотр и полную очистку истории выбранного диалога без редактирования или удаления отдельных сообщений.

Очистка краткосрочной памяти полностью удаляет историю выбранного диалога и исключает её возвращение через сводки и Sticky Facts. Записи, ранее явно сохранённые в рабочем и долговременном слоях, сохраняются. Удаление источника не должно каскадно удалять эти самостоятельные записи.

## Направления продвинутой версии

### Предложения записей с подтверждением

Модель выделяет возможные факты, решения и рабочие заметки из выбранного пользователем материала. Пользователь проверяет формулировку, выбирает слой и область действия, затем подтверждает сохранение. Неподтверждённые предложения не участвуют в сборке контекста как сохранённая память.

Стоит сравнить извлечение по отдельному действию пользователя с фоновыми предложениями. Первый вариант проще контролировать и не добавляет запрос к модели после каждой реплики. Фоновый вариант требует ограничений на стоимость, обработки ошибок и управления очередью предложений.

### Поиск по подтверждённой памяти

Сначала стоит оценить фильтры по проекту, категории и тексту. Если этого недостаточно, можно сравнить полнотекстовый поиск, семантический поиск и их сочетание. Индекс остаётся производным от записей: он не становится отдельным источником истины.

Поиск работает только внутри разрешённой области и соблюдает бюджет контекста. Пользователь должен видеть причины включения записи. Отдельно нужно проверить исключение удалённых записей из индексов и кэшей.

### Качество и актуальность фактов

Источник, дата и версия записи помогают находить ошибки и устаревшие сведения. Модель может предлагать объединение дублей, исправление противоречий и замену устаревших фактов. Любое изменение действующей памяти сохраняет требование явного выбора пользователя.

Профиль пользователя, сохранённые решения и общие знания остаются категориями долговременной памяти. Истории выполнения задач и повторно используемые инструкции можно добавить позже, если появятся конкретные сценарии. Их не следует автоматически превращать в новые слои хранения.

### Расширенная статистика

Стоит отдельно учитывать объём хранения, отбор записей для контекста и расход токенов. Число включений записи в запрос не доказывает, что модель использовала её при ответе или что ответ стал лучше.

Для дальнейшего развития полезны история включений, динамика объёма памяти, причины исключения записей и проверка качества на повторяемых сценариях. Токены по отдельным слоям и их стоимость нужно показывать как оценку, если провайдер сообщает только общий расход запроса. Учёт должен различать один пользовательский ход и несколько обращений к модели внутри него.

### Дополнительное управление

При появлении соответствующих сценариев можно рассмотреть экспорт и импорт, историю изменений, восстановление удалённых записей и сроки пересмотра. Автоматическое истечение срока записи требует отдельного решения: оно меняет доступный контекст без нового действия пользователя.

Перенос и копирование фактов между слоями должны оставаться явными действиями с понятной областью действия. Удаление записи одного слоя не означает удаление тех же сведений из остальных слоёв или исходного диалога. Удаление из всех мест хранения требует отдельной операции и отдельных правил.

## Что учесть при проектировании первой версии

- Слои используют раздельные хранилища или таблицы и отдельные операции управления. Одной общей таблицы с ненадёжной фильтрацией по типу недостаточно для требуемой изоляции.
- Каждая запись имеет стабильный идентификатор, область действия и даты. Ссылка на исходное сообщение может исчезнуть после очистки диалога; самостоятельная сохранённая запись продолжает работать.
- Сборка контекста читает слои независимо от стратегии сжатия истории. Существующий автоматический Sticky Facts не наполняет новые рабочий и долговременный слои без выбора пользователя.
- Очистка истории должна учитывать сводки, производные факты и возможность продолжения старого хода. Иначе приложение может вернуть удалённые сведения в следующий запрос.
- Глобальное закрепление и подключение записи к проекту не должны создавать неочевидные дубли. Точный способ подключения предстоит описать в дизайне.
- Массовая очистка показывает слой, область действия и число затронутых записей. Правила изменения памяти во время выполняющегося запроса требуют согласованного снимка или блокировки операции.
- Метаданные статистики не должны сохранять копию удалённого текста. Политику очистки диагностических логов и резервных копий нужно описать отдельно от очистки действующей памяти.
