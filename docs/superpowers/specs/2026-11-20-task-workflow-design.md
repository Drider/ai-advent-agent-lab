# Состояние задач и подключаемые workflow

Дата: 2026-11-20. Статус: проект для согласования.

## Назначение

Приложение сохраняет состояние каждой задачи и восстанавливает работу без повторного объяснения её цели, текущего шага и ожидаемого действия. Пользователь может подключить к задаче workflow с допустимыми этапами, переходами и проверками. Сервер проверяет действие до исполнения и переход до применения; инструкции модели не заменяют эти проверки.

Разные задачи используют разные процессы. Анкетирование, подготовка аналитического отчёта и создание кода не обязаны проходить одинаковые этапы. Проект объединяет диалоги и общую память, но не имеет единственного общего состояния задачи.

## Согласованные требования

- Состояние задачи существует независимо от подключения workflow.
- Диалог по умолчанию работает без явного workflow. Пользователь подключает процесс самостоятельно либо явно настраивает значение по умолчанию в профиле. Агент не выбирает процесс самостоятельно.
- В одном диалоге одновременно существует только одна незавершённая задача. После `done` или `cancelled` можно начать следующую. Предпочтительный сценарий — один диалог на задачу.
- Разные диалоги проекта могут вести разные задачи со своими этапами.
- Workflow подключается к текущей задаче с момента подключения и начинает работу с начального этапа. Предыдущая переписка остаётся контекстом, но не подтверждением прохождения этапов.
- Первая версия включает готовые шаблоны и пользовательские структурированные схемы. Генерация схем агентом отложена.
- Workflow хранится в отдельной библиотеке. Профили могут задавать явно настроенный процесс по умолчанию; скилл объясняет агенту работу с автоматом. Серверный контроль действует независимо от скилла.
- Утверждение плана приходит от пользователя через кнопку или точную команду и относится к конкретной версии плана.
- Для аналитики достаточно успешных формальных тестов; отдельное принятие результата пользователем не требуется.
- Задачу можно поставить на паузу на любом этапе, продолжить или явно отменить. Отмена не считается успешным завершением.
- Без workflow агент может завершить задачу после выдачи результата. Уточнение или прерывание оставляет задачу незавершённой. Пользователь также может завершить или отменить её явно.
- Анкета — необязательный workflow, который пользователь подключает на общих основаниях, как любой другой процесс. Без его подключения диалог работает без анкетирования. Область действия подключённой анкеты ограничивается текущим диалогом; между диалогами нет общей готовности пользователя.
- Для переходов применяем ACID. Вызов модели и внешние действия не входят в одну длительную транзакцию SQLite.
- Визуализация, возможный визуальный редактор и генерация схем агентом сохраняются в [отдельном roadmap](../../task-workflow-roadmap.md).

## Рассмотренные подходы

### Workflow внутри профиля

Профиль содержит инструкции и структурированную схему процесса; задача фиксирует выбранную версию. Подход уменьшает число отдельных сущностей, но связывает предпочтения пользователя с порядком работы. Для разных процессов потребуются разные профили или дополнительные переопределения. Пользователь предпочёл отдельную библиотеку.

### Отдельная библиотека workflow — выбранный подход

Библиотека хранит версионируемые процессы, а задача — применяемую версию и собственное состояние. Один профиль подходит для разных процессов. Библиотека становится общей основой для ручных схем, будущего редактора и генерации агентом.

### Только инструкции в скилле или профиле

Текст может объяснить порядок, но не обеспечивает отклонение запрещённого перехода или действия. Поэтому скилл дополняет обязательный серверный автомат, а не заменяет его.

## Текущая реализация и точки подключения

Приложение использует Nuxt, AI SDK `ToolLoopAgent` и SQLite. `server/api/chat.post.ts` загружает диалог, резервирует ход через `startMemoryAwareTurn`, готовит контекст и запускает `streamChatAgent`. Профиль и память получают снимки перед ходом. Сжатие истории не изменяет исходные сообщения.

`server/agent/recorded-tools.ts` сохраняет начало и результат вызова инструмента. `turn-repository.ts` запрещает запуск инструмента для остановленного хода и оценивает безопасность продолжения. Обычное продолжение прерванного хода сейчас отключает изменяющие инструменты. Эти ограничения сохраняются и дополняются проверками задачи.

База уже использует `WAL`, внешние ключи, `synchronous=FULL` и короткие транзакции `BEGIN IMMEDIATE`. Ревизии применяются для защиты от устаревших изменений. Отдельной сущности задачи, пользовательских аккаунтов и общего загрузчика произвольных скиллов сейчас нет. Файловые инструменты работают внутри `data/`; редактирования исходников и запуска пользовательских тестовых программ у агента нет.

## Предлагаемые решения автора

Следующие детали конкретизируют согласованные требования и входят в согласование этого документа. Они не считаются отдельными решениями пользователя до утверждения дизайна.

### Три независимых уровня состояния

| Уровень | Что описывает | Примеры |
| --- | --- | --- |
| Ход модели | Выполнение одного запроса и его восстановление. | `running`, `stopped`, `interrupted`, `needs_review`. |
| Задача | Продолжительную работу и её исход. | `active`, `paused`, `done`, `cancelled`. |
| Узел workflow | Разрешённый сейчас этап, шаг и ожидаемое действие. | Планирование / утверждение плана / подтверждение пользователя. |

Ожидание ответа пользователя не является паузой: задача остаётся `active`, а `expected` указывает ожидаемое действие. Пауза сохраняет узел и результаты без продвижения процесса. Неопределённый результат инструмента блокирует дальнейшие действия через отдельный признак восстановления, не превращаясь в этап workflow.

### Задача как данные

Снимок состояния представляет проверяемые данные. Поля этапа и шага выводятся из узла подключённого workflow; модель не может отдельно переписать их на произвольные значения.

```yaml
taskId: task-123
task: Подготовить отчёт
status: active
workflowId: analytics
workflowVersion: 1
nodeId: collect_data
nodeVisitId: visit-456
stage: execution
step: Собрать данные
expected:
  actor: agent
  kind: artifact
  artifactType: dataset
revision: 4
```

`nodeVisitId` различает повторные посещения одного узла после возврата на доработку. Утверждения и результаты проверок относятся к нужному посещению и версиям материалов. Одного совпадения названия этапа недостаточно для повторного использования старого подтверждения.

Задача также сохраняет краткую цель, заметку о прогрессе, ссылки на результаты, незакрытые вопросы и необходимые данные для следующего действия. Обязательный снимок задачи передаётся независимо от Summary, Sliding Window, Sticky Facts и отбора памяти. Его нельзя восстановить только из сводки разговора.

### Жизненный цикл без workflow

В обычном режиме `workflowId` и `nodeId` равны `null`. Сервер обеспечивает базовые переходы `active → paused → active`, `active → done` и `active/paused → cancelled`. Пользователь может явно завершить обычную задачу также из паузы; это не доступно для обхода условий подключённого workflow.

Первое обычное сообщение автоматически создаёт задачу, если незавершённой задачи нет. Следующие сообщения относятся к ней. После терминального исхода новое сообщение создаёт следующую задачу. Явное действие «Новая задача» подчиняется той же проверке единственности. Сервер не пытается по смыслу сообщения доказать, что пользователь сменил тему.

Агент обновляет прогресс, ожидаемое действие и материалы через серверные инструменты. Он запрашивает завершение с сохранённым непустым результатом, когда работа выполнена. Фраза «готово» в тексте не меняет состояние. Если агент не запросил завершение, задача остаётся активной; пользователь может завершить её явно. Ошибка, остановка или вопрос сами по себе не переводят задачу в `done`.

Запрос завершения сохраняет итоговый материал, доступный пользователю в карточке задачи, и только затем фиксирует `done`. Остановка до этой фиксации оставляет задачу незавершённой. Если поток оборвался после уже подтверждённого завершения, задача остаётся завершённой, а сохранённый результат можно открыть после перезагрузки. Дополнительный потоковый пересказ не является единственным местом хранения результата.

### Схема workflow

Первая версия использует ориентированный граф узлов, а не фиксированную глобальную цепочку этапов. Узел содержит стабильный ID, `stage`, подпись шага, ожидаемое действие, разрешённые типы материалов и доступные рабочие инструменты. Переход содержит ID, исходный и целевой узлы, допустимого инициатора и условия.

Глобальные настройки процесса определяют обязательные подтверждения и набор проверок перед успешным завершением. Названия этапов служат отображению; права задаются структурированными полями. Переименование узла в «валидация» не выдаёт права завершить задачу.

Условия выбираются из реестра серверных проверок. В схеме нет `eval`, JavaScript, shell-команд, произвольных SQL-запросов или загрузки кода. Первая версия поддерживает JSON как канонический формат и ввод JSON/YAML с преобразованием в тот же проверяемый объект.

Перед публикацией сервер проверяет формат, уникальность ID, существование начального узла и целей переходов, достижимость узлов, существование пути к успеху, известные инструменты и условия. Успешный исход обязан требовать непустой набор формальных проверок. Явные циклы доработки допустимы; автомат не проходит их самостоятельно бесконечно. Действует существующий лимит шагов хода.

Произвольное описание ожидаемого действия не становится исполняемым условием. Неизвестная проверка, инструмент или версия формата приводят к отказу, а не к пропуску ограничения.

### Версии и подключение

Опубликованная версия workflow неизменяема. Редактирование создаёт новую версию. Начатая задача продолжает использовать закреплённую версию; миграции активного процесса и его замены посередине в первой версии нет.

Подключение workflow к задаче без процесса выполняет пользователь через кнопку или точную команду. В короткой транзакции сервер фиксирует версию, начальный узел и новое посещение. Идентификатор задачи и её цель сохраняются. Старые материалы остаются контекстом; старые подтверждения, результаты проверок и вызовы инструментов не становятся доказательствами прохождения нового процесса. Для использования прежнего материала создаётся новая явная ссылка-снимок и выполняются необходимые проверки.

Если пользователь подключает процесс в пустом диалоге, сервер создаёт задачу с временным названием; первое сообщение уточняет её цель. Подключать или менять процесс во время выполняющегося хода нельзя. Для уже подключённого процесса операция повторного подключения запрещена. Отказаться от процесса можно отменой задачи и созданием новой; это не создаёт успешный исход старой задачи.

### Материалы, утверждения и проверки

Материал задачи — сохраняемый версионируемый объект: план, ответы анкеты, набор данных, предложение кода или отчёт. Он имеет тип, версию, содержимое или сохранённый снимок, хеш и сведения об источнике. Ссылки на сообщения и вызовы инструментов фиксируют происхождение; обязательный материал не должен зависеть от обрезанного текста в контексте.

План публикуется как материал, после чего сервер создаёт запрос утверждения. Кнопка и команда передают ID этого запроса. Сервер проверяет задачу, посещение узла, версию и хеш плана. Более новая версия плана требует нового утверждения. Подтверждение из другого диалога, предыдущей задачи или прежнего посещения не подходит.

Модель не имеет инструмента «утвердить от имени пользователя». HTTP-обработчик пользовательского действия и серверный инструмент агента используют общий сервис, но получают роль инициатора из доверенного контекста, а не из аргумента `actor`. Наличие реплики «да», текста «план утверждён» в памяти или `approved: true` в ответе инструмента не заменяет пользовательского события.

Формальные проверки выполняет серверный реестр. Результат содержит тип и версию проверки, версии и хеши проверяемых материалов, исход `passed/failed/error` и безопасные детали. Ошибка проверки не считается успехом. Агент может запросить запуск, но не передать готовый успешный исход.

Для первой версии реестр включает:

- Обязательные поля и типы структурированного материала, непустые значения, перечисления и числовые границы.
- Наличие обязательных разделов текстового результата по заданным заголовкам.
- Подтверждённый успешный результат конкретного инструмента. Структурная ошибка `{ ok: false }` не считается успехом только потому, что функция не выбросила исключение.
- Сопоставление сохранённого файлового результата с созданным материалом по пути и хешу прочитанных байтов. Проверка использует существующие ограничения файловой рабочей области.
- Числовые проверки над структурированным набором данных: количество, сумма, среднее и сравнение с заявленными показателями с заданным допуском. Формулы ограничены этими операциями и не исполняют пользовательский код.

Проверки используют сохранённые неизменяемые снимки входов. Новое чтение изменённого файла создаёт новую версию данных; результат старой проверки не относится к ней. Файловая проверка подтверждает наблюдавшееся содержимое, а не запрещает последующее изменение файла внешней программой.

Все зависимости проверки явные. Замена плана, набора данных или отчёта делает зависимые подтверждения и результаты непригодными для последующего перехода. Перед `done` сервер заново проверяет соответствие текущих версий. Наличие когда-либо успешной проверки недостаточно.

### Готовые процессы первой версии

**Анкета — необязательный шаблон.** Пользователь явно подключает этот workflow так же, как аналитику или создание кода. Без подключения анкета не запускается, а отсутствие её результатов не ограничивает обычную работу диалога. У автомата нет специального обязательного этапа знакомства с пользователем.

Демонстрационная схема подключённого шаблона: последовательный сбор обязательных ответов → формальная проверка заполненности → выполнение исходного запроса → проверка наличия результата → завершение. Шаблон содержит небольшой демонстрационный набор: цель обращения, уровень знакомства с темой и предпочтительный формат ответа. Пользовательская схема может менять поля. Агент задаёт вопросы и переносит ответы текущего диалога в структурированный материал с указанием источников. Только в рамках подключённого workflow неполная анкета блокирует предусмотренные его схемой рабочие инструменты и переход к исходному запросу.

В демонстрационном шаблоне анкетирование является предварительной частью текущей задачи, а не второй параллельной задачей. Это свойство схемы данного шаблона, а не общее правило диалога. Исходная цель задачи сохраняется. Заполненность анкеты сама по себе не означает выполнения исходного запроса и не переводит всю задачу в `done`.

После успешного завершения задачи ответы остаются материалом диалога. Шаблон помечает их экспортом контекста диалога; другие шаблоны по умолчанию ничего не экспортируют. Схема может перечислить типы экспортируемых материалов в `contextExports`. Контекст следующих задач включает последние успешно экспортированные версии по паре workflow/тип материала в рамках того же диалога с явным указанием происхождения. Экспортируются только данные, а не утверждения, проверки или права. Такой контекст имеет отдельный ограниченный бюджет и не переносится в другие диалоги или память автоматически. При переполнении обязательного экспортированного контекста сервер сообщает об этом, а не теряет его молча.

**Создание кода.** Подготовка плана → утверждение его версии пользователем → подготовка кода как материала → структурная валидация результата → завершение. До утверждения запрещены материалы типа `implementation` и рабочие действия выполнения. Первая версия демонстрирует управление процессом, но не добавляет редактирование репозитория, сборку и запуск тестов созданного кода. Проверка явно называется структурной; она не выдаётся за доказательство работоспособности программы. Подключение настоящих инструментов разработки потребует отдельного адаптера проверок.

**Аналитический отчёт.** План → утверждение → сбор структурированных данных → подготовка отчёта → формальные тесты → завершение. Для воспроизводимой демонстрации входом служит JSON-набор записей с числовым полем `value`; отчёт содержит источники, количество, сумму, среднее и текстовые разделы «Данные», «Результаты», «Выводы». Сервер независимо рассчитывает показатели по сохранённому набору, проверяет структуру, разделы и файловый результат. Ошибочная сумма, неполные данные или отсутствующий отчёт блокируют `done`. Отдельное пользовательское принятие отчёта не требуется.

Это ограниченный формальный контракт отчёта. Корректность произвольного аналитического вывода не следует из проверки разделов или арифметики. Другие виды аналитики требуют соответствующего набора поддерживаемых проверок.

Для кода и аналитики предусмотрены явные возвраты из валидации на выполнение и из выполнения на пересмотр плана. Пересмотр плана сбрасывает пригодность старого утверждения. Процесс нельзя завершить прямым переходом из планирования.

### Контроль действий и граница гарантии

Сервер проверяет не только запрос перехода, но и вызов каждого рабочего инструмента, запись материала и успешное завершение. Скрытие инструмента от модели служит подсказкой; обёртка его `execute` остаётся обязательной защитой. Подмена имени этапа или аргументов не обходит сервис.

В `prepareStep` агент получает актуальный снимок задачи, ожидаемое действие и доступные операции. Перед исполнением сервер заново проверяет текущий узел, посещение, статус, условия и незавершённые операции. Если переход и рабочее действие попали в один параллельный пакет, рабочее действие не получает новые права в том же пакете: изменение посещения требует следующего шага агента с новым снимком.

Пауза, отмена и смена узла блокируют новые действия уже работающего хода. Завершившийся позже инструмент может сохранить квитанцию о фактическом результате, но не продвинуть отменённую задачу и не изменить новую. Неизвестные инструменты запрещены для явного workflow до назначения прав в схеме.

Гарантия относится к сохраняемому состоянию, официальным материалам, инструментам и исходу задачи. Свободный текст модели остаётся вероятностным: автомат не доказывает, что фраза не содержит преждевременно написанный код или неподтверждённый вывод. Такой текст не меняет этап и не создаёт подтверждённый результат. Первая версия не добавляет семантический фильтр всех потоковых ответов.

### Отклонённый переход

Запрещённое действие возвращает структурированную ошибку с текущим состоянием, причиной и разрешённым следующим действием. Например: `PLAN_APPROVAL_REQUIRED`, `TRANSITION_NOT_ALLOWED`, `VALIDATION_REQUIRED`, `STALE_TASK_REVISION`, `TASK_PAUSED`, `TASK_CANCELLED`, `RECOVERY_REVIEW_REQUIRED`.

В момент отказа этап, шаг, материалы и ревизия задачи не меняются. Сервис может сохранить отдельное событие отказа в журнале команд; оно не является применённым переходом. Агент объясняет причину и предлагает разрешённый путь. Повторный запрос «пропусти план и сразу заверши» должен получить тот же отказ. Повторяющиеся отказы ограничиваются существующим лимитом шагов; сервер не ослабляет условия для выхода из цикла.

### ACID, повтор запросов и внешние действия

Одна команда состояния выполняет в `BEGIN IMMEDIATE` чтение актуальной задачи, проверку `expectedRevision`, роли, перехода и доказательств, запись нового состояния и события, а также квитанции команды. Уникальный `operationId` делает повтор той же команды идемпотентным. Повтор ID с другим содержимым возвращает конфликт.

- Атомарность: принятие команды, новый снимок и событие сохраняются вместе; при ошибке частичного перехода нет.
- Согласованность: сервер проверяет инварианты, ограничения схемы, актуальность доказательств и единственность незавершённой задачи.
- Изоляция: короткая транзакция и ревизия не позволяют двум обращениям незаметно перезаписать состояние.
- Долговечность: подтверждённые данные сохраняются существующей конфигурацией SQLite и доступны после перезапуска.

Для отказа транзакция команды завершается записью отрицательной квитанции без изменения задачи. Ошибка сохранения самой квитанции не превращается в разрешение действия.

Внешнее действие использует протокол намерение → исполнение вне транзакции → подтверждённый результат. Существующий журнал инструментов расширяется привязкой к задаче, посещению и стабильному ключу операции. Ключ повторного выполнения связан с сохранённым намерением, а не только с новым ID вызова модели. Подтверждённое действие не повторяется при возобновлении.

База и файловая система не образуют общую ACID-транзакцию. При сбое после записи файла, но до подтверждения в базе задача получает блокировку восстановления. Проверяемый путь и хеш позволяют сверить результат; при неразрешимой неопределённости пользователь явно подтверждает фактический исход. Подтверждение восстановления не подменяет формальные тесты результата. Универсальная гарантия exactly-once для произвольных внешних инструментов не заявляется.

### Пауза, отмена и продолжение

Кнопка «Пауза» сначала фиксирует паузу и останавливает текущий ход, затем прерывает поток. Новые инструменты после фиксации паузы запрещены. Уже начатое внешнее действие может завершиться; его квитанция сохраняется отдельно, без продвижения узла. Возобновление недоступно, пока результат такого действия остаётся неопределённым.

«Продолжить задачу» возвращает её в `active` и запускает новый обычный ход с сохранёнными целью, узлом, материалами, подтверждениями и следующим действием. Разрешены новые рабочие операции, но не повтор уже подтверждённых. Новые сообщения по-прежнему блокируются, если в диалоге остаётся работающий ход или неразрешённое восстановление.

Существующее «Продолжить ответ» для прерванного хода сохраняет ограничение изменяющих инструментов. Это отдельная операция от возобновления задачи. Остановка генерации не означает автоматическую паузу или отмену задачи: она сохраняет её прогресс и отмечает прерванный ход.

Отмена разрешена из любого незавершённого состояния и фиксирует `cancelled`. Пользователь может начать следующую задачу после остановки старого хода и разрешения неопределённых внешних операций. Отмена не откатывает уже выполненные внешние действия и не переводит их результаты в успех новой задачи. Терминальные задачи в первой версии не открываются повторно.

### Контекст, профили и память

Перед каждым ходом сервер фиксирует профиль как сейчас и загружает задачу. Перед шагами агента обновляет её операционный снимок; изменение профиля внутри хода не заменяет уже зафиксированный профиль. В конфигурации хода сохраняются ID задачи, начальная ревизия, версия workflow и хеш снимка, а в метаданных шагов — применённые ревизии состояния.

Снимок задачи и материалы, обязательные для текущего узла, имеют отдельный лимит размера и входят в оценку контекстного окна. Если обязательный контекст не помещается, запрос завершается явной ошибкой до нового вызова модели. Нельзя молча опустить состояние, план для утверждения или требуемые результаты. Лимиты материалов соотносятся с существующим пределом текстовых файлов 16 КиБ; конкретные ограниченные размеры схем и материалов определяет план реализации.

Память проекта остаётся общей для его диалогов, а долговременные факты сохраняют текущие области действия. Автомат не создаёт и не изменяет записи памяти автоматически. «Сохрани в память проекта» продолжает означать явное сохранение в существующий рабочий слой. Новую область task-scoped memory первая версия не добавляет.

Проектные `state`, `goal` и `constraint` передаются как данные общей памяти и не заменяют состояние активной задачи. Отбор памяти может включить сведения о другой задаче проекта; это не даёт им прав управления процессом. Независимые задачи никогда не читают чужие утверждения или проверки как собственные доказательства.

Профиль получает необязательный `defaultWorkflowId`, по умолчанию `null`. Пользователь меняет его в интерфейсе профиля явным действием. Создание следующей задачи использует актуальную опубликованную версию явно настроенного процесса, если пользователь не выбрал «Без workflow». Смена профиля не подключает и не заменяет процесс уже существующей задачи. Инструмент редактирования текста профиля не получает право менять это поле.

Скилл первой версии — группа `server/tools/tasks/` с `SKILL.md`, инструкциями для агента и инструментами. Он подключается к существующему агенту как часть приложения. Установка внешнего Codex-скилла или общий менеджер пользовательских скиллов в эту работу не входят. Базовые инструменты состояния работают всегда; инструкции явного процесса добавляются только при его подключении.

### Ветки, очистка и миграция

Ветка наследует контекст и профиль по существующим правилам, но не активную задачу, утверждения или проверки родителя. Она создаёт независимую задачу при первом сообщении или явном подключении процесса. Выбранный для новой задачи процесс начинает работу с начального узла; старые tool parts в скопированной истории остаются контекстом. Явно настроенный профильный процесс по умолчанию действует как для новой задачи, а не как копия состояния родителя.

Очистка истории диалога удаляет его задачи, материалы, утверждения, проверки и журналы команд вместе с сообщениями и ходами. Это производные и рабочие данные диалога, а не самостоятельные записи памяти. Рабочая и долговременная память сохраняются по существующим правилам; созданные внешние файлы не удаляются автоматически. Операция запрещена при работающем ходе или неразрешённом внешнем действии. Ссылки на очищенные источники в памяти обнуляются, а старые ID запросов и инструментов остаются заблокированными от повтора. Удаление диалога удаляет его задачи каскадно.

Миграция не пытается восстановить достоверное состояние задач из старых разговоров. Существующие диалоги получают отсутствие явного workflow; их следующая новая реплика создаёт обычную задачу, а старая история остаётся контекстом. Для старых прерванных ходов «Продолжить ответ» сохраняет прежнее поведение без создания фиктивных подтверждений. После такого продолжения новый обычный запрос создаёт задачу.

### Хранилище и серверные границы

Предлагаемые таблицы:

| Таблица | Назначение |
| --- | --- |
| `workflows`, `workflow_versions` | Библиотека, метаданные и неизменяемые схемы опубликованных версий. |
| `tasks` | Задача, её состояние, ревизия, версия процесса, посещение узла и данные продолжения. |
| `task_artifacts` | Неизменяемые версии планов, данных и результатов с хешами и происхождением. |
| `task_approvals` | Запросы и пользовательские подтверждения конкретных материалов. |
| `task_validations` | Фактические результаты серверных проверок с зависимостями. |
| `task_events`, `task_commands` | Применённые изменения, отказы и идемпотентные квитанции команд. |

Частичный уникальный индекс по диалогу для `status IN ('active', 'paused')` обеспечивает единственность незавершённой задачи независимо от API и модели. Ходы и вызовы инструментов получают nullable-ссылки на задачу для совместимости со старыми данными. Подтверждения и проверки не хранятся как редактируемые булевы поля задачи.

Сервис `server/tasks/` содержит чистую проверку переходов, транзакционные команды, политику инструментов, реестр формальных проверок и подготовку контекста. `shared/task.ts` и `shared/workflow.ts` задают общие контракты. HTTP API, инструменты модели и команды чата вызывают один сервис; отдельных обходных путей обновления `stage` нет.

Минимальные группы API:

- Библиотека `/api/workflows`: список, чтение версии, создание и публикация новой проверенной версии.
- Задачи диалога `/api/sessions/:id/tasks`: история задач и явное создание следующей задачи.
- Пользовательские действия `/api/tasks/:id/actions`: подключение, пауза, продолжение, отмена, утверждение, завершение обычной задачи и разрешение восстановления.
- Чтение `/api/tasks/:id`: снимок, доступные пользовательские действия, материалы и история переходов.

Все изменяющие действия принимают `operationId` и `expectedRevision`; привязку к диалогу и роль проверяет сервер. Лимиты и ошибки нормализуются единообразно.

Инструменты агента: чтение текущей задачи, обновление заметки прогресса, сохранение разрешённого материала, запрос разрешённого перехода, запуск проверки и запрос завершения. Они привязаны к серверным `sessionId/turnId/taskId`. Модель не передаёт другую задачу, роль пользователя, успешный результат теста или команду отключения контроля. Переходы и изменение состояния журналируются и как операции задачи, и через существующий учёт вызовов инструментов; эти квитанции согласуются в одной транзакции для операций внутри базы.

### Минимальный интерфейс

Используем существующий Nuxt UI и оформление приложения. Первая версия добавляет компактную карточку состояния и текстовый редактор схем; графы не входят в её объём.

```text
Задача: Подготовить отчёт                  Активна
Workflow: Аналитика · v1
Этап: Планирование · Утверждение плана
Ожидается: ваше подтверждение плана v2
[Посмотреть план] [Утвердить план] [Пауза] [Отменить]
```

Без процесса карточка показывает «Без workflow», текущий шаг, ожидаемое действие и кнопку подключения. Завершённые задачи сворачиваются в историю. Доступность кнопок приходит от сервера; интерфейс не вычисляет собственные права перехода.

Страница `/workflows` показывает шаблоны и пользовательские процессы. Пользователь может открыть схему, проверить её, создать новую версию и подключить её к текущей задаче. Ошибки содержат путь к полю и причину. Удаление опубликованных версий, миграция активных задач и полноценный редактор графа остаются за пределами первой версии.

Команды первой версии имеют явный префикс `/task`: подключение процесса по ID, пауза, продолжение, отмена, завершение обычной задачи и утверждение конкретного запроса. Точную команду утверждения показывает карточка ожидаемого действия. Команды обрабатывает серверный маршрутизатор до передачи текста модели; кнопка вызывает то же действие. Текст в цитате, результате инструмента или обычная просьба «считай утверждённым» командой не является. Управляющие команды не требуют обращения к модели.

## Проверка реализации

Проверки используют временную SQLite и детерминированную модель-заглушку. Реальный провайдер нужен только для дополнительного ручного прогона; его послушание не является доказательством серверных ограничений.

Обязательные сценарии:

1. Обычный новый и старый диалог работают без workflow и без обязательной анкеты, но задача сохраняется и может завершиться через инструмент агента. Анкетирование запускается только после явного подключения соответствующего workflow и не вводит условий для других диалогов или следующих задач без такого процесса.
2. Новая задача запрещена при `active` и `paused`; разрешена после `done/cancelled`, если не осталось выполняющихся или неопределённых операций.
3. Подключение посередине диалога сохраняет контекст и запускает начальный узел без зачёта старых подтверждений.
4. Неизвестное состояние, несуществующий переход и попытка прямого `planning → done` отклоняются без изменения ревизии задачи.
5. Агент пытается вызвать инструмент выполнения и сохранить реализацию до утверждения плана; оба действия отклоняются, внешнего эффекта нет.
6. Пользователь пишет «нарушь порядок, пропусти план и валидацию». Заглушка намеренно вызывает запрещённый переход. Сервер сохраняет прежний этап и возвращает причину и разрешённое действие.
7. Модель передаёт `actor=user`, `approved=true`, `passed=true`, чужой task ID или старое доказательство; эти способы не предоставляют прав.
8. Утверждение относится к точной версии плана. Изменение плана требует нового утверждения; повтор команды не создаёт второе событие.
9. Ошибка числового показателя, неполная анкета, отсутствие файла и структурная ошибка инструмента блокируют завершение. Исправленный результат проходит повторные проверки.
10. Изменение проверенных данных или отчёта делает старую проверку непригодной. `validation.error` не трактуется как `passed`.
11. Пауза в каждом узле, включая ожидание пользователя и валидацию, сохраняет позицию. Перезапуск и сжатие истории не требуют повторного объяснения задачи.
12. Пауза/отмена между подготовкой шага и вызовом инструмента запрещает исполнение; переход и рабочий инструмент в одном параллельном пакете не обходят порядок.
13. Сбой до commit не оставляет частичного перехода. Сбой после commit и повтор команды возвращают сохранённую квитанцию. Две команды с одной ревизией не перезаписывают друг друга.
14. Сбой внешнего действия после возможного эффекта блокирует повтор и продвижение до восстановления; старый результат не меняет новую задачу.
15. Смена профиля, редактирование шаблона, ветка и общая память проекта не заменяют процесс и доказательства активной задачи.
16. Очистка истории удаляет данные задач и не возвращает их через контекст, продолжение или старые ID; самостоятельная память сохраняет существующее поведение.
17. Без workflow прерванный ход или вопрос не завершают задачу автоматически. Потоковый текст «готово» не меняет официальный статус.
18. Состояние и обязательные материалы учитываются в бюджете контекста; переполнение вызывает явную ошибку без запуска агента с неполными ограничениями.

После реализации нужны соответствующие тесты репозиториев, API и агента, существующие регрессионные проверки сохранения, продолжения, веток, памяти и профилей, затем `npm run typecheck`, `npm test` и `npm run build`.

## Границы первой версии

Первая версия не добавляет аккаунты, общую анкету пользователя между диалогами, параллельные задачи внутри диалога, перенос задач между диалогами, генерацию или выбор workflow агентом, визуальные графы, произвольные исполняемые проверки, полноценную среду разработки и автоматическое сохранение состояния в память.

Выбор внутренней организации компонентов, конкретных ограниченных размеров, реализации JSON/YAML-разбора и порядка миграций остаётся автору плана при сохранении указанных контрактов. Для конечного автомата достаточно небольшого собственного проверяемого сервиса поверх существующей SQLite; отдельная библиотека оркестрации не требуется.
