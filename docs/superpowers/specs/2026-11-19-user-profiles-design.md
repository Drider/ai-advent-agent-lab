# Профили пользователя для персонализации агента

Статус: проект для согласования.

## Назначение

Пользователь задаёт дополнительные инструкции о предпочтительном стиле ответов,
формате и ограничениях. Именованных профилей может быть несколько. Каждый диалог
использует один выбранный профиль; новые диалоги получают профиль по умолчанию.
Профили доступны без авторизации, сохраняются между перезапусками и управляются
через отдельную страницу и инструменты агента.

Профиль — самостоятельная сущность. Он не является долговременной памятью,
не создаёт записи категории `profile` и не меняет существующие области памяти.

## Согласованные требования

- Можно создавать несколько профилей, редактировать их и переключать профиль
  конкретного диалога.
- Для новых диалогов есть профиль по умолчанию. Смена этого значения не меняет
  выбор в существующих диалогах.
- Редактирование доступно на отдельной странице; редактирование и выбор также
  доступны по явному запросу пользователя из чата.
- Полный текст выбранного профиля подключается при каждом ходе агента.
- Текст профиля не сокращается, не отбирается по релевантности и не сжимается
  вместе с историей.
- Профили не связаны с авторизацией и не объединяются с памятью агента.

## Подходы

1. **Общий активный профиль приложения.** Меньше состояния, но переключение
   в одном диалоге меняет поведение всех остальных. Рассмотрен и отклонён.
2. **Профиль на диалог и значение по умолчанию для новых — выбран пользователем.**
   Позволяет вести несколько диалогов с разными предпочтениями. Требует хранить
   выбор в сессии и отдельно хранить профиль по умолчанию.

Для хранения используем существующую SQLite: браузер и серверные инструменты
получают общий источник истины. Local storage не подходит для управления
профилями агентом. Включение профиля только в историю не подходит, поскольку
история может сжиматься или отсекаться.

## Предлагаемые решения

Следующие детали выбраны автором дизайна и подлежат согласованию вместе с ним.

### Содержимое профиля

Первая версия содержит только два редактируемых поля:

- `name`: название, от 1 до 80 символов после удаления внешних пробелов;
- `instructions`: единый многострочный текст дополнительных инструкций,
  от 0 до 16 000 кодовых единиц UTF-16. Внутреннее форматирование сохраняется;
  отдельные поля для стиля, формата и ограничений пока не вводятся.

Служебные поля: UUID, `revision`, время создания и изменения. Пустой текст
разрешён: такой профиль не добавляет предпочтений к базовому поведению агента.
Название уникально после NFKC-нормализации, приведения к нижнему регистру
и удаления внешних пробелов. Коллизия имени возвращает ошибку, а не перезаписывает
другой профиль. Некорректный Unicode, NUL, неизвестные поля и неверные типы
отклоняются общими валидаторами API, репозитория и инструментов.

При миграции создаётся пустой профиль «Основной». Он назначается всем существующим
диалогам и становится значением по умолчанию. В новой базе используется тот же
порядок. Поэтому у любого диалога всегда есть профиль, даже до ввода предпочтений.

### Хранение и жизненный цикл

- Таблица `user_profiles` хранит профили и нормализованный уникальный ключ имени.
- Одна строка настроек хранит `default_profile_id` с внешним ключом.
- `sessions.user_profile_id` ссылается на профиль. Назначение обязательно
  для существующих и новых сессий.
- Создание диалога читает значение по умолчанию на сервере в той же транзакции,
  в которой создаёт сессию. Клиент не назначает его задним числом.
- Ветка наследует профиль родительского диалога на момент создания ветки.
- Диалоги хранят ссылку на профиль, а не независимые копии. Редактирование профиля
  влияет на следующие ходы всех диалогов, которые его используют.
- Изменение профиля использует `expectedRevision`. При конфликте возвращается 409;
  интерфейс сохраняет несохранённый черновик и предлагает загрузить актуальную
  версию, не затирая её автоматически.
- Изменение выбора увеличивает ревизию сессии и возвращает актуальный профиль.
  Само редактирование профиля не обновляет даты всех связанных диалогов.
- Удаление профилей, импорт и экспорт не входят в первую версию: они не требуются
  для создания, редактирования и переключения и добавляют правила переназначения.

### Подключение к агенту

При начале хода сервер атомарно читает назначенный профиль и резервирует ход.
Фиксируется снимок `id`, `name`, `revision`, `instructions`. Этот снимок
используется на всех шагах текущего запуска. Редактирование или переключение
в середине ответа начинает действовать со следующего пользовательского хода.
Команда продолжения считается новым ходом и получает актуальный профиль.

Полный текст снимка добавляется отдельным явно обозначенным блоком к инструкциям
агента. Базовые правила работы с инструментами сохраняют приоритет. Профиль задаёт
предпочтения по умолчанию; более конкретная просьба пользователя в текущем
сообщении может их переопределить. Название профиля передаётся как метаданные,
а не как дополнительные команды.

Эффективные инструкции и их хеш должны соответствовать друг другу в `getAgentConfig`,
сохранённом `agent_config_json` и фактическом `ToolLoopAgent`. В конфигурации хода
также сохраняются идентификатор и ревизия профиля, чтобы можно было установить,
какой текст использовался. Не допускается отдельная сборка инструкции, которая
учитывает профиль только для логирования или только для оценки размера.

Самостоятельный блок профиля не добавляется как реплика в пользовательскую историю,
не попадает в checkpoint или Sticky Facts и не передаётся служебным вызовам
суммаризации. Он добавляется к каждому основному обращению модели, включая шаги
после инструментов, при всех стратегиях: `off`, `summary`, `sliding_window`,
`sticky_facts`.

Если пользователь обсуждал текст профиля в сообщениях или получил его через
инструмент, эти исторические сообщения обрабатываются как обычная история
и могут сжиматься. Они не заменяют актуальный самостоятельный блок профиля
и не считаются источником действующих настроек. Выделять и удалять из истории
такие упоминания не требуется.

Оценка входного контекста и `promptOverheadTokens` учитывает полный блок профиля.
Если обязательные инструкции и текущий запрос не помещаются в допустимый бюджет,
сервер возвращает понятную ошибку до сохранения новой пользовательской реплики
и запуска модели. Профиль молча не обрезается; уже существующие проверки бюджета
после результатов инструментов также учитывают его.

### Интерфейс

Сохраняем оформление существующего приложения и компоненты Nuxt UI.
В шапке чата показываем выбор профиля и ссылку на страницу `/profiles`.
Список не смешивается с конфигурациями моделей и страницей памяти.

```text
Диалог: План работы
Профиль: [Краткие ответы ▾]   [Профили]   [Память]
```

Выбор в чате применяется сразу после успешного сохранения на сервере; при ошибке
остаётся предыдущий выбор и показывается причина. Во время генерации переключатель
в интерфейсе недоступен; серверный endpoint также отклоняет такое переключение
с 409. Инструмент текущего агента имеет отдельное разрешённое поведение ниже.

Страница `/profiles` совмещает список профилей и форму редактирования выбранного:

```text
Профили                         [Вернуться в чат]

[Основной · по умолчанию]        Название
[Краткие ответы]                [Краткие ответы           ]
[Для обучения]                  Дополнительные инструкции
[+ Создать профиль]             [Опишите предпочтения:     ]
                                [стиль, формат, ограничения ]
                                [                          ]
                                [Сохранить]
                                [Использовать по умолчанию]
```

На странице явно написано: изменения профиля применятся со следующего сообщения
во всех диалогах с этим профилем. Назначение по умолчанию — отдельное действие
и меняет только будущие диалоги. Создание профиля не переключает существующий
диалог и не делает его значением по умолчанию автоматически.

При открытии из чата передаём контекст возврата и выбранный профиль. После
возвращения или завершения хода с инструментами чат перечитывает назначение
и список профилей. Ошибки загрузки, сохранения и конфликты показываются рядом
с соответствующим действием. Несохранённые правки защищаются подтверждением
при смене редактируемого профиля и при уходе со страницы. Постоянная синхронизация
между вкладками не нужна: сервер всегда использует актуальное назначение.

### API и общие правила

Используем существующие Nuxt server routes и репозитории. Предлагаемые операции:

- `GET /api/user-profiles` — список профилей без полных инструкций и ID значения
  по умолчанию;
- `POST /api/user-profiles` — создать профиль;
- `GET /api/user-profiles/:id` — получить полный профиль;
- `PATCH /api/user-profiles/:id` — изменить переданные `name` и/или `instructions`
  с обязательным `expectedRevision`; пропущенные поля сохраняются;
- `PATCH /api/user-profiles/default` — назначить существующий профиль по умолчанию;
- `PATCH /api/sessions/:id/user-profile` — выбрать профиль диалога, когда нет
  выполняющегося хода.

Чтение сессии возвращает ID и актуальную краткую информацию о назначенном профиле.
Все записи проходят через репозиторий; API и инструменты не дублируют SQL.
Обычные ошибки: 400 для неверных данных, 404 для отсутствующей сущности,
409 для конфликта имени, ревизии или занятого диалога. Применяем `no-store`
к ответам с пользовательскими профилями.

### Инструменты и скилл агента

Добавляем группу `server/tools/user-profiles/` с `index.ts`, README и `SKILL.md`,
по существующему примеру конфигураций моделей. Инструкции, необходимые при
выполнении, реально подключаются к агенту; один файл `SKILL.md` без подключения
не считается работающим скиллом. Динамический загрузчик произвольных скиллов
для этой задачи не нужен.

Инструменты:

- `list_user_profiles` — названия, ID, ревизии, выбранный и профиль по умолчанию;
- `get_user_profile` — полный профиль по ID; без ID возвращает назначенный
  текущему диалогу;
- `create_user_profile` — создать профиль с указанными пользователем названием
  и инструкциями;
- `update_user_profile` — изменить переданные поля по ID и `expectedRevision`;
- `select_user_profile` — назначить существующий профиль текущему диалогу.

Создание, изменение и переключение выполняются только по явному запросу.
Агент не выводит предпочтения из поведения пользователя и не копирует их
из долговременной памяти самостоятельно. Перед семантическим изменением текста
агент получает полную текущую версию и сохраняет все не затронутые просьбой
инструкции. При неоднозначном названии уточняет выбор; не придумывает ID
и не подменяет профиль с похожим названием. Результаты включают точную сохранённую
версию и указание, что изменения применятся к генерации со следующего хода.

`select_user_profile` получает привязанные сервером `sessionId` и `turnId`:
их нельзя передать аргументами модели. Он может менять выбор своего диалога
во время выполнения собственного активного хода, но не другого диалога или
уже остановленного хода. Снимок инструкций текущего хода при этом не меняется.
Редактирование общего профиля также не изменяет уже выполняющиеся генерации.

Все инструменты проходят через `recordToolExecution`, чтобы изменения были
видны в диалоге и учитывались при восстановлении. В режиме безопасного
продолжения доступны только `list_user_profiles` и `get_user_profile`;
существующий запрет повторных изменяющих действий сохраняется. Назначение
по умолчанию в первой версии меняется на странице профилей.

## Границы первой версии

- Нет авторизации, владения профилями и разделения доступа к истории или памяти.
  Переключение профиля меняет инструкции, а не набор доступных данных.
- Нет автоматического заполнения или изменения профиля из переписки и памяти.
- Нет иерархий, объединения нескольких профилей, переопределений по проектам
  и отдельных структурированных полей предпочтений.
- Нет удаления, импорта, экспорта и новой общей инфраструктуры загрузки скиллов.
- Нет изменения инструкций посреди одного запуска агента и переписывания
  ответов или сохранённых checkpoint после редактирования профиля.

## Проверка результата

Проверяем сценарии, которые могут нарушить основной контракт:

1. Миграция существующей и создание чистой базы назначают профиль всем сессиям;
   после перезапуска сохраняются тексты, назначения и значение по умолчанию.
2. Новый диалог получает текущий профиль по умолчанию, смена default не затрагивает
   существующие, ветка наследует родительский профиль.
3. Независимый выбор двух диалогов сохраняется; редактирование общего профиля
   применяется на следующем ходе каждого из них.
4. Полный самостоятельный блок профиля присутствует в эффективных инструкциях
   при всех стратегиях и нескольких шагах агента, отдельно не добавляется
   в суммаризацию или пользовательскую историю, учитывается при проверке бюджета.
5. Снимок текущего хода не меняется после редактирования или выбора инструментом;
   следующий ход использует новый снимок. Переполнение не обрезает профиль
   и не оставляет принятую пользовательскую реплику без запущенного хода.
6. Инструменты используют общий репозиторий, сохраняют незатронутые поля,
   обрабатывают конфликт ревизии и не меняют чужой/остановленный диалог.
   Безопасное продолжение не допускает изменяющих инструментов.
7. В браузере создаём и редактируем профиль, выбираем его в двух диалогах,
   меняем default и проверяем новый диалог; проверяем ошибки и сохранение черновика.

После реализации выполняем подходящие Vitest-тесты, `npm run typecheck`,
`npm run build` и проверку основных действий в браузере.

## Что остаётся исполнителю

Разбивка на файлы и задачи, точная организация composable и компонентов,
механизм передачи снимка между существующими функциями, детали миграционного
SQL и единый формат типизированных ошибок. Эти решения должны соблюдать
описанные правила и существующие соглашения репозитория.
