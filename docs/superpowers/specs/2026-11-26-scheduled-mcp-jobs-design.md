# Планировщик заданий с MCP и отчётами за период

## Назначение

Пользователь пишет в чат, что и когда собирать. Приложение сохраняет задание и выполняет его без открытой вкладки чата, пока запущен сервер Nuxt. Каждый фактический запуск оставляет запись в SQLite. По отдельному расписанию появляется отчёт за период, рассчитанный по всем запускам этого периода.

## Решение для первого этапа

- Чат превращает запрос в структурированное задание: имя, источник, параметры источника, расписание сбора, расписание отчёта, часовой пояс и инструкция для текстовой сводки. Перед сохранением сервер проверяет поля и доступность выбранного источника. По умолчанию используется `SCHEDULER_DEFAULT_TIMEZONE=Europe/Moscow`; если времени или источника нет в запросе и его нельзя вывести однозначно, чат уточняет это у пользователя.
- Источники задаются оператором через `SCHEDULER_SOURCES_JSON`: массив `{ id, kind: "http_json", url, allowedQueryKeys }`. Начальный каталог также содержит встроенный источник `clock` для сквозной проверки. Источник `http_json` обращается только к заранее настроенному HTTPS URL. Промпт не может указать произвольный адрес или команду. Формат источника расширяемый; новые виды источников требуют кода, а новые экземпляры `http_json` — только конфигурации.
- Локальный stdio MCP-сервер `scripts/scheduler-mcp-server.mjs` предоставляет `get_data`, `save_result`, `read_period`. Первый инструмент получает JSON выбранного источника, второй сохраняет результат с уникальным `runId`, третий постранично читает все успешные результаты в интервале. MCP-сервер использует тот же `data/chat.sqlite`, что и Nuxt, с WAL и внешними ключами. По умолчанию приложение запускает этот файл через текущий Node; `SCHEDULER_MCP_SERVER_JSON` позволяет заменить команду. Подключение отделено от `MCP_SERVERS_JSON`, чтобы внутренние инструменты сохранения не попадали в обычный набор инструментов чата.
- Фоновый цикл стартует из Nitro plugin при запуске серверного процесса, не из HTTP-запроса или вкладки. Он хранит задания и очередные сроки в SQLite, забирает каждый срок под уникальным ключом и вызывает `get_data` → `save_result` через существующий MCP-клиент. Ошибки получения и сохранения фиксируются как неуспешные запуски, а не пропадают.
- Расписание задаётся пятичастными cron-выражениями с именованным IANA часовым поясом. Запуски и границы отчётов хранятся в UTC. Период отчёта — `[предыдущий срок отчёта, текущий срок отчёта)`; данные на текущей границе относятся к следующему периоду. Если процесс проснулся не позднее пяти минут после срока сбора, он выполняет запуск; более старые сроки помечаются `missed` без ретроспективного запроса к источнику. Просроченные отчёты строятся по уже накопленным результатам. Это исключает выдачу сегодняшних данных за вчерашние.
- Отчёт содержит проверяемую часть: границы периода, количество успешных, неуспешных и пропущенных запусков, количество сохранённых результатов и доступный постранично список идентификаторов вошедших результатов. Текстовая сводка строится из всех страниц `read_period`; большие наборы обрабатываются частями с финальным объединением. Если модель недоступна, проверяемая часть сохраняется, а текстовая часть получает статус ошибки.
- Задания и отчёты доступны через API и страницу приложения. Из чата можно создать, перечислить и приостановить задание, а также открыть готовый отчёт. Сводка создаётся по расписанию и остаётся доступной после закрытия чата и перезапуска приложения.

## Надёжность и ограничения

- Один срок сбора соответствует одной строке `scheduled_runs` с уникальным `(job_id, scheduled_for)`. `save_result` идемпотентен по `runId`; повторное сохранение не создаёт второй результат. При аварии между запросом к источнику и записью результат может быть потерян, поэтому зависший запуск получает явный статус `failed`. Если результат уже записан, восстановление завершает запуск как `completed`. Это не обещает ровно один внешний запрос при любом сбое.
- Один активный экземпляр фонового цикла выбирается через SQLite lease с продлением; второй сервер не выполняет те же сроки параллельно. После аварии lease истекает, новый экземпляр сверяет зависшие запуски с сохранёнными результатами и продолжает расписание.
- Отчёты не удаляют исходные результаты. Пауза задания запрещает будущие запуски, но сохраняет историю. Секреты источников хранятся только в серверной конфигурации и не записываются в задание или отчёт.
- Расписание работает только пока запущен серверный процесс. Для постоянной работы приложение нужно запускать под менеджером процессов на постоянно работающем хосте. Встроенный планировщик не заменяет системный запуск приложения.

## Приёмка

1. Запрос в чат создаёт задание с точным расписанием и показывает следующий запуск; неоднозначный запрос не создаёт задание молча.
2. Закрытая вкладка чата не мешает серверу вызвать все три MCP-инструмента в нужных фазах.
3. Два и более срока сбора создают разные записи; после перезапуска они остаются в SQLite.
4. Отчёт за период включает каждый успешный результат этого периода и не включает результат вне границ; повторная генерация не создаёт дубль.
5. Ошибка MCP или модели видна в истории; она не подменяется пустым успешным результатом.
6. Одновременные серверные циклы и повторный тик не исполняют один срок дважды.
7. Страница показывает задания, статусы запусков и готовые отчёты после перезапуска приложения.
