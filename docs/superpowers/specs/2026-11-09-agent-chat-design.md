# Простой чат с агентом: описание решения

## Зачем это нужно

Нужен небольшой веб-чат для общения с агентом через OpenAI-совместимый API. Главная учебная цель — показать настоящего агента: модель может запросить инструмент, получить его результат, снова обратиться к модели и повторять этот цикл до итогового ответа. Первый инструмент бросает виртуальный кубик.

Пользователь пишет обычный запрос, например «Брось кубик» или «Брось d20», и видит результат. Если тип кубика не назван, используется d6. Можно выбрать модель для следующего сообщения. Адрес и ключ LLM API, а также модель по умолчанию задаются на сервере через `.env`.

## Согласованные требования

- Агент — отдельная серверная сущность. Серверный маршрут принимает и проверяет запрос, передаёт его агенту и возвращает поток ответа. Промпт, список инструментов, вызовы модели, выполнение инструментов и цикл до ответа принадлежат агенту.
- После каждого вызова инструмента его результат поступает обратно модели. Она может запросить следующий инструмент; цикл заканчивается, когда она выдаёт итоговый ответ без новых вызовов.
- Первый инструмент выдаёт случайный результат одного броска кубика с указанным числом граней; по умолчанию это d6.
- В интерфейсе из настроек есть только выбор модели. Секреты не вводятся в браузере.
- Сохранение переписки и интерфейс истории чатов будут отдельной задачей. С самого начала нужны диагностические логи общения с агентом по образцу `ai-app`.
- Внешний вид близок к [предоставленному скриншоту](assets/agent-chat-reference.png): основной чат, поле ввода внизу, компактная область выбора модели и действие «Новая сессия». Остальные настройки со скриншота не входят в первую версию.

## Техническая основа

Новый репозиторий пока пуст. Ориентир — стек соседнего проекта `ai-app` на 2026-11-09: Node.js 22.18+, npm, Nuxt 4, Vue 3, TypeScript, Nuxt UI 4, Lucide Icons, Vercel AI SDK (`ai` 7, `@ai-sdk/vue`, `@ai-sdk/openai`), Comark и KaTeX для отображения Markdown и формул, Vitest и Nuxt Typecheck. Использовать OpenAI-совместимый Chat Completions endpoint через `createOpenAI(...).chat(model)`, как в `ai-app`. Не переносить бенчмарки и расширенные настройки оттуда.

Первый вариант рассчитан на локальный запуск одним процессом Node.js с доступной для записи папкой `data/`. Логи сохраняются на диске между перезапусками процесса. Развёртывание без постоянной файловой системы и работа нескольких серверных экземпляров оставлены для отдельной задачи; это наше решение о границах первой версии.

Для агента использовать отдельный модуль/фабрику на базе `ToolLoopAgent` из AI SDK 7. Этот класс инкапсулирует многошаговый цикл и потоковый ответ. Фабрика создаёт агента с выбранной моделью, инструкциями и инструментами. Клиент использует `useChat` из `@ai-sdk/vue`; серверный маршрут отдаёт совместимый поток UI-сообщений. Историю текущей вкладки клиент передаёт с каждым сообщением. Серверного хранилища контекста в этой версии нет.

## Поведение чата

1. При открытии используется `LLM_MODEL_DEFAULT`; в поле модели можно ввести ID другой модели. Выбор применяется к следующему сообщению, включая сообщения в уже открытом диалоге. ID проверяется перед отправкой.
2. Пользователь отправляет текст. Во время ответа видны состояние ожидания и затем потоковый текст. Отправка второго сообщения до завершения текущего блокируется. Ошибка выводится рядом с чатом, сообщение пользователя остаётся для повтора.
3. Агент решает, нужен ли инструмент. Обычный вопрос допускает прямой ответ. Просьба бросить кубик требует вызова инструмента; агент не придумывает случайное число сам.
4. Инструмент получает число граней и возвращает результат в диапазоне от 1 до этого числа включительно. «Брось кубик» означает d6, «Брось d20» — один бросок двадцатигранного кубика. Если пользователь просит несколько бросков, агент вызывает инструмент для каждого броска и сообщает все результаты.
5. «Новая сессия» очищает сообщения и черновик в текущей вкладке, создаёт новый идентификатор лога и возвращает модель по умолчанию. Перезагрузка страницы также начинает пустой диалог. Просмотра прежних сессий нет.
6. Вызов инструмента может отображаться как компактный статус «Бросаю кубик…», но итоговый ответ остаётся главным содержимым чата. Технический JSON инструмента пользователю не показывается.

## Инструмент броска кубика

Инструмент выполняется на сервере и использует `crypto.randomInt` из Node.js, чтобы получать число без участия модели. Внешний сервис и дополнительный ключ ему не требуются. Это наш выбор реализации.

- Вход инструмента — целое число граней `sides`. При отсутствии типа кубика агент передаёт `6`.
- Поддержать обозначения `dN` для одного кубика с `N` гранями, где `N` — целое число от 2 до 1000. Такой предел защищает от бессмысленных или ошибочных аргументов; это наш выбор для первой версии.
- Выход инструмента — `{ sides, result }`, где `1 ≤ result ≤ sides`. Каждый вызов генерирует новое число. Модель получает результат и дословно использует его в ответе.
- Некорректный тип, например `d0`, `d1` или дробное число граней, приводит к понятному сообщению об ошибке. Поддержка записи количества вида `2d6` как отдельного синтаксиса не требуется: просьбу о нескольких бросках агент выполняет несколькими вызовами инструмента.

## Границы агентного цикла

Нормальный путь: запрос к модели → ноль или больше вызовов инструментов → передача каждого результата модели → итоговый ответ, после которого инструменты больше не запрашиваются. Агент допускает несколько последовательных запросов инструмента в одном пользовательском сообщении.

Для защиты от зацикливания и лишних расходов на модель установить предел в 10 шагов и общее время выполнения. Достижение предела считается незавершённым ответом и явно показывается как ошибка; нельзя выдавать промежуточный текст за итоговый. Точный механизм ограничения и отмены выбирается при реализации в рамках возможностей AI SDK 7.

Модель, выбранная пользователем, должна поддерживать tool calling у подключённого OpenAI-совместимого провайдера. Если провайдер отвергает вызовы инструментов, показать понятную ошибку без молчаливого перехода на другой режим.

## Конфигурация и безопасность

Пример `.env.example`:

```dotenv
LLM_BASE_URL=https://api.example.com/v1
LLM_API_KEY=your-llm-api-key
LLM_MODEL_DEFAULT=your-model-id
LLM_LOG_LEVEL=basic
```

`LLM_BASE_URL` и `LLM_API_KEY` обязательны для полного сценария; если `LLM_MODEL_DEFAULT` не указан, использовать значение `deepseek/deepseek-v4.1-flash` из `ai-app`. `LLM_LOG_LEVEL` по умолчанию равен `basic`. Ключ остаётся в приватной конфигурации Nuxt, `.env` и папка логов исключены из Git. В браузер передаются только ID модели и необходимые данные чата. Сервер проверяет структуру входных сообщений и ID модели, ограничивает размер запроса и не включает секреты в сообщения об ошибках или логи.

## Диагностические логи

Следовать устройству `ai-app`: `LLM_LOG_LEVEL=off|basic|detailed|raw` (по умолчанию `basic`), один `data/runs/run-<runId>.json` на диалог, добавление записи после каждого обращения пользователя, последовательная и атомарная запись файла. `runId` создаётся для текущей сессии и меняется по «Новой сессии».

- `basic`: вопрос, итоговый ответ или статус ошибки, время начала и окончания, длительность, суммарный расход токенов за все шаги.
- `detailed`: также модель, отправленный контекст, метаданные завершения, порядок шагов и вызовы инструментов с аргументами, результатами или ошибками.
- `raw`: также исходные фрагменты ответа LLM-провайдера, если они доступны через SDK.
- `off`: не создавать файл лога.

Логи нужны для диагностики и не образуют доступную пользователю историю. Ошибка записи лога фиксируется на сервере и не уничтожает готовый ответ. В логах не сохраняются ключи API и URL с ключом в параметрах.

## Не входит в первую версию

Архив и восстановление диалогов, аккаунты, база данных, список доступных моделей от провайдера, другие инструменты, ручные настройки температуры/рассуждений/лимита токенов, бенчмарки и отчёты `ai-app`.

## Проверка результата

- Обычный запрос получает потоковый ответ без вызова инструмента.
- «Брось кубик» вызывает инструмент с `sides=6` и даёт ответ от 1 до 6. «Брось d10» и «Брось d20» дают результаты в соответствующих пределах.
- Сценарий с несколькими последовательными вызовами инструмента доходит до итогового ответа. Лимит шагов останавливает зацикливание с явной ошибкой.
- Ответ содержит именно значение, возвращённое инструментом; некорректное число граней отклоняется.
- Смена модели влияет на следующий запрос; ключи не попадают в браузер.
- «Новая сессия» и обновление страницы очищают чат, а файлы логов продолжают существовать только как диагностические данные.
- Все четыре уровня логирования дают ожидаемый состав данных; записи одного диалога попадают в один файл.

## Оставлено реализатору

Конкретная структура компонентов и файлов, значения таймаутов, способ отображения статуса инструмента и дизайн на малом экране, пока они соблюдают описанное поведение.
