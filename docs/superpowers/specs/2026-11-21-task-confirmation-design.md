# Надёжное подтверждение этапов и проверка анкеты

## Основание и фактическое состояние

Основание: приложенный пользователем разбор инцидента «Три отдельных дефекта…»,
`docs/task-lifecycle.md` и текущая незакоммиченная реализация на `master`.

В реализации есть `/task approve`: команда разбирается в `shared/task.ts`,
перехватывается в `ChatWorkspace.vue`, вызывает `PATCH /api/sessions/:id/task` и
применяет переход в транзакции `task-repository.ts`. Панель получает результат
PATCH. Следующий ход агента получает свежий `<task_state>`, включая ответы анкеты.
Поэтому формулировки «команда не существует», «нет никакого чтения ответов» и
«повторный запрос создаёт стек pending» к этому коду не относятся.

Пробелы остаются: `request_task_transition` возвращает только
`awaitingUserConfirmation: true`, его описание не называет механизм
подтверждения; у агента нет read-инструмента для повторной проверки в текущем
ходе; итог действия пользователя не коррелирует с запросом перехода; в
`review` нельзя изменить один ответ. UI-подтверждение происходит после
завершения хода модели, поэтому никакой инструмент внутри исходного хода не
может дождаться клика. Реакция модели возможна лишь в новом ходе.

Подтверждение `onboarding → done` уже создаёт и выбирает профиль через
`completeOnboarding`. Недостаёт предпросмотра точного текста профиля перед
этим подтверждением.

## Целевой контракт

Единый серверный снимок задачи строится из SQLite и определения шаблона:

```ts
interface TaskSnapshot extends TaskState {
  revision: number // увеличивается при любой записи задачи, включая ответы
  allowedTransitions: string[]
  pendingTransition: {
    id: string
    to: string
    summary: string
    requestedAt: string
    expiresAt: string
  } | null
  lastTransition: {
    id: string
    to: string
    outcome: 'approved' | 'rejected' | 'expired' | 'cancelled'
    resolvedAt: string
  } | null
  questions: Array<{
    id: string
    prompt: string
    required: boolean
    answered: boolean
    value?: string
  }>
  completed: boolean
}
```

Унаследованный `TaskState` сохраняет `goal`, `step`, `artifacts`, `answers`,
временные метки и старые `pendingStage`/`pendingSummary` для существующего UI.

`get_task_state({})` читает этот снимок без побочных эффектов. Он доступен
агенту на любом этапе открытой задачи, в том числе при паузе и pending.
При отсутствии задачи возвращает `{ ok: true, task: null }`. Сервер выводит
`allowedTransitions` из графа этапов, ответы — из `answers_json`; история чата
не является источником этих значений. `revision` относится ко всей задаче, а
не только к этапу: иначе он не защитит исправление ответа.

`request_task_transition({ to, summary, expectedRevision? })` возвращает
`{ ok, applied, from, to, revision, pendingTransitionId, allowedTransitions,
confirmationHint }`. Новый запрос даёт `applied: false` и ID ожидающего
перехода. `confirmationHint` содержит только действия UI: кнопку
«Подтвердить» в панели задачи и поддерживаемую команду `/task approve`; агент
не придумывает синтаксис. Повтор того же запроса с той же сводкой возвращает
существующий ID; запрос в уже достигнутый этап возвращает `applied: true`
без новой заявки. Другой запрос при активном pending даёт конфликт со свежим
снимком. В случае ошибки ответ также содержит допустимые переходы. Остальные
инструменты задачи возвращают свежий `TaskSnapshot` при успехе и
`allowedTransitions` в структурированной ошибке: агент получает граф этапов
из сервера, а не восстанавливает его из текста диалога.

Пользовательское подтверждение/отклонение передаёт ID pending и ожидаемую
`revision`; сервер проверяет оба значения внутри транзакции. Для старого
клиента временно сохраняется `stage` вместо ID. Повтор подтверждения того же
ID возвращает тот же итог. Существующие `pendingStage`/`pendingSummary` и
`awaitingUserConfirmation` поддерживаются как устаревшие поля в переходный
период и удаляются после обновления всех клиентов.

Pending живёт 7 календарных дней, в том числе во время паузы. Чтение только
вычисляет истечение и показывает `lastTransition: expired`; оно не пишет в БД.
Первая последующая мутация атомарно закрывает истёкшую заявку. После истечения
агент может предложить переход снова. `cancel_task_transition(id)` снимает
активную заявку без смены этапа; для пользователя сохраняется `reject`.

Запросы и их исходы хранятся в отдельной таблице `task_transitions` с уникальным
активным запросом на задачу. `pendingStage`/`pendingSummary` в старой таблице
остаются совместимыми полями и обновляются в той же транзакции. Хранение всей
истории переходов позволяет повтору старого ID вернуть прежний исход даже
после следующих переходов; одного поля `lastTransition` для этого мало.

После PATCH интерфейс показывает подтверждённый/отклонённый этап и предлагает
«Продолжить задачу». Это действие запускает новый обычный ход с контекстом
задачи; агент сначала вызывает `get_task_state` и видит исход по ID. Если
понадобится автоматическая реакция без второго клика, её следует делать
отдельным серверным `task_event`-ходом, а не поддельным сообщением пользователя.
До появления такого хода UI не обещает ответ агента сразу после подтверждения.

## Анкета и профиль

Сохранение ответа возвращает записанное значение и число оставшихся вопросов;
агент подтверждает его пользователю. `amend_task_answer({ questionId, answer,
expectedRevision })` разрешён на `review` без отката в `interview` и запрещён
при активном pending. `get_task_state` возвращает исправленное значение.

В `review` панель показывает имя и точный `instructions` будущего профиля,
сформированные той же функцией, что используется при создании. Кнопка
завершения подтверждает именно эту ревизию анкеты. При конфликте ревизии или
имени предпросмотр обновляется до повторного подтверждения; профиль не
создаётся дважды.

Форма из пяти полей и enum для `level`/`style` — отдельное улучшение UX после
надёжного контракта. Текущие свободные ответы сохраняются без потерь; новые
значения `level` соответствуют текущему вопросу: `beginner`, `intermediate`,
`expert`; `style`: `brief`, `detailed`. Неизвестный старый текст не
преобразуется догадкой и предлагается к исправлению на `review`.
Время `recordedAt` не входит в минимальный снимок: существующий `answers_json`
его не хранит, а для надёжного чтения значения оно не требуется.

## Наблюдаемость и критерии готовности

- События `requested`, `approved`, `rejected`, `expired`, `cancelled` содержат
  `taskId`, `pendingTransitionId`, `revision`, время и исход. Из них считаются
  длительность до `done`, число ходов и доля повторных запросов.
- Заявления агента о смене этапа проверяются по снимку/событию перехода;
  регулярное выражение по тексту может быть лишь сигналом для ручной проверки.
- Перезагрузка страницы и нового хода сохраняет pending, ответы и последний
  исход; никакой ответ не реконструируется из истории диалога.
- Клик после истечения, двойной клик, повтор запроса и правка ответа между
  чтением и подтверждением дают детерминированный результат без лишнего
  перехода и без создания дубликата профиля.
