# Five File Tools Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Добавить агенту пять простых инструментов для локальных текстовых файлов и продемонстрировать последовательные цепочки и несколько независимых вызовов в одном шаге модели.

**Architecture:** Существующий `ToolLoopAgent` получает пять дополнительных инструментов через `createFileTools({ rootDir })`. Файловые операции и обработка текста реализуются обычными TypeScript-функциями; адаптеры `tool({ inputSchema, execute })` описывают их модели. Текущий агентный цикл, поток ответа и логгер используются повторно.

**Tech Stack:** Текущие зависимости проекта: Node.js 22.18+, TypeScript 5.9, Nuxt 4.6.4, `ai@7.0.162`, `zod@4.6.7`, Vitest 5. Новые зависимости не нужны.

**Spec:** Требования этой задачи зафиксированы в разделе «Контракты и поведение» ниже. Существующая архитектура чата описана в [2026-11-09-agent-chat-design.md](../specs/2026-11-09-agent-chat-design.md); этот план расширяет её список инструментов.

## Global Constraints

- Добавить все пять ранее предложенных имён: `find_files`, `read_file`, `search_text`, `text_stats`, `write_file`.
- Файлы находятся в `data/` относительно каталога запуска сервера. Агент получает только относительные пути внутри этой папки; `.env` и исходники находятся вне неё, а `data/runs/` и `data/dice-rolls.csv` теперь входят в тот же защищённый корень.
- `rootDir` можно передать фабрике только из серверного кода, прежде всего для временной папки в тестах. У модели такого аргумента нет.
- Сохранить `rollDie`, `listSavedRolls`, текущие лимиты `MAX_AGENT_STEPS = 10` и `AGENT_TIMEOUT_MS = 30_000`, отмену запроса и существующие уровни логирования.
- Один локальный процесс и постоянная файловая система, как в текущем приложении. Для первой версии `write_file` только создаёт новый файл; перезапись не добавляется.
- Все лимиты ниже — предлагаемые решения для первой версии, а не ранее согласованные пользователем значения.
- Не добавлять зависимости, отдельный планировщик цепочек, новый HTTP API или настройки интерфейса.
- В рабочей папке уже есть пользовательские незакоммиченные изменения, в том числе в агенте, тестах, README и `.gitignore`. При реализации прочитать актуальный diff, сохранить эти изменения и включать в коммиты только собственные изменения этапа.

## Контракты и поведение

Каждый инструмент возвращает JSON одного формата:

```ts
type ToolResult<T> =
  | { ok: true; data: T }
  | { ok: false; error: { code: ToolErrorCode; message: string } }

type ToolErrorCode =
  | 'INVALID_INPUT' | 'INVALID_PATH' | 'NOT_FOUND' | 'NOT_A_FILE'
  | 'ALREADY_EXISTS' | 'TOO_LARGE' | 'NOT_TEXT' | 'SCAN_LIMIT' | 'IO_ERROR'

interface FindFilesData { paths: string[]; truncated: boolean }
interface ReadFileData { path: string; text: string }
interface SearchTextData {
  matches: Array<{ lineNumber: number; line: string }>
  truncated: boolean
}
interface TextStatsData { lines: number; words: number; characters: number }
interface WriteFileData { path: string; bytesWritten: number }
```

Эти типы и константы лимитов находятся в `server/tools/files/file-tool-contracts.ts`.

| Инструмент | Вход модели | `data` успешного результата |
| --- | --- | --- |
| `find_files` | `{ pattern: string }` | `FindFilesData` |
| `read_file` | `{ path: string }` | `ReadFileData` |
| `search_text` | `{ text: string, query: string }` | `SearchTextData` |
| `text_stats` | `{ text: string }` | `TextStatsData` |
| `write_file` | `{ path: string, content: string }` | `WriteFileData` |

Правила первой версии:

- Пути используют `/`, имеют длину 1–512 символов, не содержат NUL, `\`, абсолютный путь или сегмент `..`. Итоговый путь обязан оставаться внутри корня. Симлинки в путях чтения и записи отклоняются; поиск их пропускает и не обходит.
- `find_files` поддерживает glob-маски, например `notes/*.md` и `notes/**/*.md`. Использовать обход `readdir({ withFileTypes: true })` без симлинков и стандартный `path.matchesGlob` для относительных путей. Маска имеет длину 1–256 символов и такие же ограничения на выход из корня, как путь. Возвращать только обычные файлы, пути сортировать лексикографически.
- Поиск возвращает первые 50 совпадений и `truncated: true`, если совпадений больше. Обход ограничен 1000 записями каталога суммарно, включая подкаталоги; превышение даёт `SCAN_LIMIT`, а не неполный успешный результат. Сортировка и выбор первых 50 происходят после обхода в пределах этого лимита.
- Отсутствующий корень при поиске равнозначен пустой папке: `{ paths: [], truncated: false }`. Чтение отсутствующего файла даёт `NOT_FOUND`. Корень и родительские папки создаются при записи.
- `MAX_TEXT_BYTES = 16 * 1024`: максимальный размер файла при чтении и записи и текста в `search_text`/`text_stats`. Размер проверяется в UTF-8 байтах; превышение даёт `TOO_LARGE`, без молчаливого усечения. Чтение ограничивается 16 КиБ + 1 байт, чтобы не загружать большой файл целиком. Некорректный UTF-8 или NUL в прочитанном файле дают `NOT_TEXT`.
- `search_text` ищет буквальную подстроку с учётом регистра, без regex. `query` имеет длину 1–256 символов. Возвращается одна запись на подходящую строку с номером от 1; максимум 100 записей с признаком `truncated` при наличии следующих совпадений.
- Строки разделяются `\r\n`, `\n` или `\r`. Пустой текст имеет 0 строк; завершающий разделитель не создаёт дополнительную строку. Слова — непустые фрагменты между пробельными символами. Символы — Unicode code points исходного текста, включая пробельные символы и переводы строк; emoji `😀` считается одним символом.
- `write_file` принимает UTF-8 текст, включая пустой. Создаёт файл с `flag: 'wx'`; существующий путь даёт `ALREADY_EXISTS`. Два конкурентных вызова на один путь дают один успех и одну ошибку, существующее содержимое сохраняется.
- Ожидаемые ошибки операций возвращаются как `ToolResult`, с понятным сообщением без абсолютных серверных путей. Zod проверяет форму аргументов до `execute`; ошибку схемы передаёт модели стандартный механизм AI SDK. Сбой файловой системы не маскируется пустым успешным результатом.
- Содержимое файлов считается данными: инструкции внутри него не должны менять задачу агента. Итоговую сводку составляет модель по фактическим результатам функций.

## Review Focus

1. `../`, абсолютные пути, общий префикс соседних каталогов и симлинки не дают читать или создавать файлы вне корня — Task 1 и Task 3.
2. Большой файл, длинный текст или слишком большая папка дают ограниченный, явно обозначенный результат — Task 1, Task 2 и Task 4.
3. Кириллица, emoji, пустой текст и разные переводы строк имеют определённые счётчики и номера строк — Task 2.
4. Повторная или конкурентная запись одного отчёта не уничтожает его содержимое — Task 3.
5. Несколько tool calls в одном шаге действительно выполняются независимо, каждый результат приходит модели, зависимые вызовы идут следующим шагом — Task 5.

## Критерии готовности

- Все пять функций доступны текущему агенту, прежние два инструмента продолжают работать.
- Автоматический тест проходит цепочку `поиск → чтения → поиск строк и статистика → сохранение → ответ` на реальных временных файлах.
- Отдельный тест подтверждает перекрывающееся выполнение двух независимых инструментов и передачу обоих результатов модели.
- Ошибки, лимиты и усечение имеют явный результат; запись отчёта не перезаписывает существующий файл.
- Тесты, проверка типов и сборка проходят; статус ручной проверки с реальным провайдером указан отдельно.
