# Задача: исправить замечания ревью жизненного цикла задач

> Статус: к исполнению. Исходный план: [2026-11-21-task-lifecycle.md](2026-11-21-task-lifecycle.md).

## Контекст

В рабочем дереве `master` лежит незакоммиченная реализация конечного автомата задач:

- `shared/task.ts`;
- `server/persistence/task-repository.ts`;
- `server/tools/tasks/`;
- `server/api/sessions/[id]/task.*.ts`;
- `components/TaskPanel.vue`;
- правки в `server/agent/chat-agent.ts`, `server/memory/start-turn.ts` и `components/ChatWorkspace.vue`.

Сейчас `npm test` (330 тестов) и `npm run typecheck` проходят. Ревью нашло одну ошибку и несколько мелочей. Ниже они перечислены по приоритету. Исправь всё, что перечислено, и ничего сверх этого.

## 1. Завершённая или отменённая задача остаётся в инструкциях агента (ошибка)

**Где:**
- `server/agent/chat-agent.ts:80` — `...(task ? [taskInstructions(task)] : [])`;
- `server/agent/chat-agent.ts:109` — `...(task ? { task: … } : {})`.

**Проблема:** `createTaskRepository(db).getForSession()` возвращает последнюю задачу диалога с любым статусом. Поэтому после `done` или `cancel` каждый следующий ход этого диалога всё ещё получает блок `<task_state>` с правилами «Work only on the current stage» и «Only the user changes the stage». После отмены агент может продолжить работу над отменённой задачей. По плану блок нужен только открытой задаче.

**Исправление:**
- Добавь в `shared/task.ts` функцию `isTaskOpen(task): boolean` (статус `active` или `paused`).
- Используй её в `buildAgentInstructions` и `getAgentConfig`: блок `<task_state>` и поле `task` в конфигурации появляются только для открытой задачи.
- Повторно используй `isTaskOpen` в `taskBlocksWrites` и в `TaskPanel.vue` (`openTask`) вместо дублирующихся проверок статуса.

**Тест:** в `tests/memory-start-turn.test.ts` или рядом с ним. Для задачи в статусах `done` и `cancelled` в `agentConfig.instructions` нет `<task_state>`, в `agentConfig` нет `task`, и `taskBlocksWrites` возвращает `false`.

## 2. `approve` определяет конечный этап не по тому этапу

**Где:** `server/persistence/task-repository.ts:204`.

```ts
const terminal = getTaskStage(candidate)?.next.length === 0 || stage === 'done'
```

**Проблема:** у `candidate` текущий, исходный этап, а не целевой. Первое условие всегда ложно, и всё держится на захардкоженном `stage === 'done'`. Если в шаблоне последний этап будет называться иначе, задача останется `active` на конечном этапе и заблокирует старт новой задачи (уникальный индекс открытых задач).

**Исправление:** проверяй целевой этап и убери хардкод:

```ts
const terminal = getTaskStage({
  templateId: task.templateId,
  stage,
})?.next.length === 0
```

**Тест:** в `tests/task-repository.test.ts`. Подтверждение `validation → done` ставит статус `done`, подтверждение `validation → execution` оставляет `active`. Если сделать это просто, добавь в тесте временный шаблон с конечным этапом под другим именем (например, `released`) и убери его в `afterEach`.

## 3. `/task approve` без ожидающего перехода даёт непонятную ошибку

**Где:** `components/ChatWorkspace.vue:214-218`.

**Проблема:** если `props.session.task?.pendingStage` нет, клиент отправляет `PATCH` без `stage`. Сервер отвечает 400 «stage is required for this action».

**Исправление:** для `approve` и `reject` без `pendingStage` не отправляй событие. Вместо этого запиши в `taskCommandError` «Нет перехода, ожидающего подтверждения.».

## 4. Блок `<task_state>` показывает действие агента, когда ход за пользователем

**Где:** `server/agent/chat-agent.ts:63`.

```ts
`Expected agent action: ${stage?.agentAction}`
```

**Проблема:** строка не учитывает паузу и ожидающий переход, а `getExpectedAction` уже есть в `shared/task.ts`.

**Исправление:**
- Замени строку на `Expected action: ${getExpectedAction(task)}`.
- Добавь в блок правило: если ожидаемое действие за пользователем (пауза или ожидающий переход), напомни ему команду и не продвигай задачу.

## 5. Мелочи

- `server/agent/chat-agent.ts:130`: опция `taskTools?: TaskTools` в `options` у `createChatAgent` не используется, потому что инструменты передаются позиционным параметром. Удали её. Поле `taskTools` во входе `streamChatAgent` (строка 250) используется, его не трогай.
- `ChatWorkspace.vue:205` и `parseTaskCommand`: `startsWith('/task')` перехватывает и `/tasks…`. Распознавай команду по `/^\/task(\s|$)/u` в обоих местах.
- `parseTaskCommand`: `split(/\s+/u)` склеивает многострочную цель в одну строку. Для `start` разбирай текст регулярным выражением вида `/^\/task\s+start\s+(\S+)\s+([\s\S]+)$/u` и сохраняй переводы строк в цели, обрезав только внешние пробелы.

**Тесты:** дополни `tests/task-state.test.ts`:
- `/tasks` не распознаётся как команда;
- многострочная цель сохраняет перевод строки.

## Ограничения

- Не меняй схему БД, HTTP API, шаблоны этапов и поведение, которого нет в этом списке.
- Стиль:
  - в `interface` и `type` обязательные поля идут выше необязательных;
  - объектный литерал с вложенным объектом и объект, возвращаемый из функции (если в нём больше одного поля), пиши по одному полю на строку с завершающей запятой.
- Не коммить. Если попросят закоммитить: сообщение на русском, в третьем лице, глаголом в начале (например, «Исправляет …»), без Conventional Commits и без строк атрибуции (`Co-Authored-By` и т. п.).

## Дополнительно, если есть доступ к модели

Пройди ручной сценарий из раздела «Проверка» исходного плана в `npm run dev` (порт 3535). Отчитайся по каждому шагу:
