# Планировщик фоновых заданий

Планировщик собирает данные по одному расписанию и создаёт отчёты по другому. Задание хранится в SQLite и продолжает выполняться без открытой вкладки чата, пока работает сервер Nuxt. Cron-выражение задаёт моменты запуска; оно не запускает отдельный системный процесс и не задаёт срок жизни задания.

## Быстрый старт

Укажите в `.env` источник данных и часовой пояс. Для встроенного источника времени достаточно такой конфигурации:

```dotenv [.env]
SCHEDULER_ENABLED=true
SCHEDULER_DEFAULT_TIMEZONE=Europe/Moscow
SCHEDULER_SOURCES_JSON='[{"id":"clock","kind":"clock","allowedQueryKeys":[]}]'
```

Настройте `LLM_BASE_URL` и `LLM_API_KEY` по [инструкции запуска](../README.md#запуск), затем запустите приложение через `npm run dev`. Создайте задание в чате, например:

```text [Запрос в чате]
Собирай данные из clock каждые 2 минуты. Раз в 10 минут делай отчёт по всем значениям за период в часовом поясе Europe/Moscow. Для каждой метки времени UTC вычисли GMST и покажи таблицу.
```

Агент проверяет источник и параметры, сохраняет задание и сообщает время следующего сбора и отчёта. Откройте `/schedules`, чтобы увидеть состояние задания, последние запуски и отчёт. Страница обновляет данные каждые 15 секунд.

## Настройки задания

| Поле | Значение |
| --- | --- |
| `name` | Название в списке заданий и заголовке отчёта. |
| `sourceId`, `sourceQuery` | Источник из `SCHEDULER_SOURCES_JSON` и разрешённые параметры запроса. |
| `collectCron` | Когда получать данные. |
| `reportCron` | Когда закрывать период и формировать отчёт. |
| `timezone` | Часовой пояс IANA для расчёта обоих расписаний, например `Europe/Moscow`. |
| `summaryInstruction` | Что LLM должна сделать с собранными значениями. |
| `modelId` | Необязательная модель для отчётов. Без неё используется `LLM_MODEL_DEFAULT` или модель приложения по умолчанию. |

Планировщик принимает пятичастные cron-выражения: `минута час день_месяца месяц день_недели`. Поля принимают числа, `*`, списки через запятую, диапазоны через `-` и шаги через `/`; названия месяцев и дней недели не поддерживаются. Секунд и даты окончания в формате задания нет. Например, `*/2 * * * *` запускает сбор каждые две минуты, а `*/10 * * * *` создаёт отчёт каждые десять минут. Планировщик рассчитывает эти моменты в часовом поясе задания и хранит следующие сроки в UTC.

Новые задания сразу получают статус `active` и работают без фиксированной даты завершения. Через чат можно перечислить задания, поставить задание на паузу и возобновить его. Страница `/schedules` позволяет удалить задание вместе с его запусками и отчётами; удаление во время активного запуска возвращает ошибку, поэтому повторите его после завершения. Редактирования существующего задания нет: чтобы изменить расписание или инструкцию, создайте новое задание и удалите старое.

## Как выполняется расписание

Сервер запускает фоновый цикл при старте Nuxt и проверяет сроки примерно каждые 15 секунд. Для каждого срока сбора он вызывает локальный MCP-сервер: `get_data` получает значение источника, а `save_result` сохраняет его в `data/chat.sqlite`. Уникальная пара «задание — срок» защищает от повторной записи одного запуска.

Если сервер пропустил срок сбора не более чем на пять минут, планировщик выполняет его при следующей проверке. Более старые сроки он помечает как `missed`: данные источника задним числом не запрашиваются. Ошибка получения или сохранения данных создаёт запуск со статусом `failed` и текстом ошибки.

Каждый срок отчёта закрывает полуоткрытый период `[предыдущий срок отчёта, текущий срок отчёта)`. Значение, собранное точно на конечной границе, относится к следующему периоду. Отчёт хранит количество успешных, неуспешных и пропущенных запусков, а также ссылки на сохранённые результаты периода.

Для непустого периода LLM формирует текст по `summaryInstruction`. Планировщик передаёт модели все сохранённые результаты частями и при необходимости просит объединить части в итоговую сводку. Пустой период получает сообщение об отсутствии результатов без вызова LLM. Если модель или чтение результатов завершается ошибкой, отчёт сохраняет проверяемые количества со статусом `failed`; новый отчёт по следующему сроку всё равно планируется. Готовый отчёт также появляется сообщением ассистента в чате, где было создано задание, пока этот чат существует.

Цикл обрабатывает задания последовательно. Пока LLM составляет отчёт, следующий сбор может ждать её ответа. После завершения отчёта планировщик проверяет накопившиеся сроки; для сборов по-прежнему действует правило пяти минут.

## Источники и запуск сервера

Встроенный источник `clock` возвращает текущее время UTC. Для JSON API добавьте источник вида `http_json` с заранее известным URL и списком разрешённых параметров:

```dotenv [.env]
SCHEDULER_SOURCES_JSON='[{"id":"weather","kind":"http_json","url":"https://example.com/weather","allowedQueryKeys":["city"]}]'
```

Источник `http_json` принимает HTTPS, а для локального сервиса также HTTP на `localhost`, `127.0.0.1` или `::1`. URL выбирается из серверной конфигурации: запрос в чате не может подставить произвольный адрес. После изменения `.env` перезапустите Nuxt. Если удалить источник из конфигурации, задания с его `sourceId` начнут завершать сбор ошибкой.

Внутренний MCP-сервер запускается автоматически из `scripts/scheduler-mcp-server.mjs`; добавлять его в `MCP_SERVERS_JSON` не требуется. `SCHEDULER_MCP_SERVER_JSON` позволяет заменить его команду запуска, а `SCHEDULER_ENABLED=false` отключает фоновый цикл.

Задания и результаты переживают перезапуск благодаря SQLite, но cron-выражение само не поддерживает запущенный процесс. Когда Nuxt остановлен, в том числе после закрытия терминала с `npm run dev`, сроки не исполняются. Для непрерывной работы держите сервер запущенным под менеджером процессов; после его запуска планировщик обработает накопившиеся сроки по правилам выше.

## Проверка и неполадки

Страница `/schedules` показывает статус, следующий сбор, следующий отчёт, последние запуски и последний отчёт. Полную историю одного задания можно получить через `GET /api/schedules/{id}`, а список заданий — через `GET /api/schedules`.

| Наблюдение | Что проверить |
| --- | --- |
| Следующий срок прошёл, новых запусков нет | Работает ли сервер Nuxt, не задано ли `SCHEDULER_ENABLED=false`, имеет ли задание статус `active`. |
| Запуск имеет статус `missed` | Сервер или цикл вернулся к этому сроку позднее пяти минут; старые значения источника не восстанавливаются. |
| Запуск имеет статус `failed` | Откройте ошибку запуска. Проверьте `sourceId`, разрешённые параметры и доступность источника. |
| Отчёт имеет статус `running` дольше обычного | Планировщик может ждать LLM. Пока она отвечает, другие задания в том же цикле тоже ждут. |
| Отчёт имеет статус `failed` | Откройте ошибку отчёта. Проверьте настройки LLM, доступность модели и чтение результатов через MCP. |
| После паузы или перезапуска появились пропуски | Планировщик сохраняет прежние сроки; при возобновлении он помечает сборы старше пяти минут как `missed`. |

Для резервной копии работающей базы используйте `npm run backup:chat`. Обычное копирование файла `data/chat.sqlite` во время работы сервера не включает гарантированно все данные из WAL.
