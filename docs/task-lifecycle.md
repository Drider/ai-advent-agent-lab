# Жизненный цикл задач

Задача закрепляет работу агента за формальным конечным автоматом. Шаблон и
цепочка этапов определены в коде, а текущая задача хранится в SQLite вместе с
целью, шагом, артефактами, ответами анкеты и ожидающим подтверждения переходом.

## Шаблоны и переходы

| Шаблон | Цепочка |
| --- | --- |
| `dev` / Разработка | `planning → execution → validation → done` |
| `bugfix` / Исправление ошибки | `diagnosis → planning → execution → validation → done` |
| `onboarding` / Анкетирование | `interview → review → done` (из `review` можно вернуться в `interview`) |

Этап `execution` — единственный этап, на котором агент получает
`write_file`. Валидация может перейти либо в `done`, либо обратно в `execution`
для доработки. Терминальный `done` появляется только после `validation`.

Агент не меняет этап самостоятельно. Он вызывает
`request_task_transition({ to, summary, expectedRevision? })`, а сервер сохраняет
заявку с `pendingTransitionId`, сроком действия семь дней и ревизией. Ответ
`applied: false` означает, что этап ещё не изменился. Пользователь подтверждает
или отклоняет заявку кнопкой в панели либо командами `/task approve` /
`/task reject`; повтор по тому же ID идемпотентен, а конфликт ревизии возвращает
свежий снимок.

`get_task_state({})` читает актуальный `TaskSnapshot` прямо из SQLite без
активного хода и без записи. После пользовательского действия новый ход агента
сначала читает этот инструмент; заявлять о смене этапа можно только по
`applied: true` или по свежему снимку.

## Команды

Команды разбираются клиентом и не отправляются модели:

```text
/task start dev Сделать отчёт по docs/*.md в report.md
/task start bugfix Исправить ошибку в обработке PDF
/task approve
/task reject
/task pause
/task resume
/task cancel
```

Для `approve` и `reject` клиент передаёт `pendingTransitionId` и
`expectedRevision`; старое поле `stage` временно поддерживается для совместимости.
Сервер всё равно проверяет ID, ревизию и граф переходов; подмена даёт
`STAGE_MISMATCH` или `REVISION_CONFLICT`.

## Пауза и продолжение

Пауза разрешена на любом открытом этапе, в том числе когда агент уже предложил
переход. Пока задача на паузе, новые предложения отклоняются с
`TASK_PAUSED`, а ожидаемое действие вычисляется как `/task resume`. После
продолжения задача сохраняет этап, шаг, цель и pending-предложение, поэтому
перезагрузка страницы или сжатие истории не требуют повторять объяснение цели:
снимок `<task_state>` добавляется в инструкции каждого нового хода.

Пользовательские действия заблокированы во время активного хода (`SESSION_RUNNING`),
а вызовы инструментов агента привязаны к конкретному активному `turnId`.

## Артефакты и история

После подтверждения сводка сохраняется в `artifacts` под исходным этапом. Это
позволяет агенту видеть утверждённый план и результаты после паузы. История
диалога не используется как единственный источник состояния.

Ветка диалога не наследует задачу: после создания ветки она стартует без неё.
Удаление диалога каскадно удаляет задачи. Завершённая или отменённая задача
остаётся видна в панели, но новая открытая задача может быть начата в том же
диалоге.

## Анкета

Шаблон `onboarding` начинается на этапе `interview` и задаёт пять вопросов:
имя, занятие, цель использования ассистента, уровень и предпочтительный стиль
ответов. Агент задаёт вопросы по одному и сохраняет каждый ответ через
`record_task_answer`. Пока ответы не сохранены, переход к `review` отклоняется
с кодом `ANSWERS_MISSING` и полем `missing` со списком id вопросов.

На этапе анкеты доступны `record_task_answer`, `update_task_step`,
`request_task_transition`, `get_task_state` и отмена pending-заявки; на паузе
read-инструмент сохраняется, а запись отвечает `TASK_PAUSED`. На этапе `review`
добавляется `amend_task_answer`: он меняет один ответ без отката в `interview`.

В `review` панель показывает точный preview будущего профиля. Кнопка завершения
передаёт имя preview вместе с ревизией; при коллизии имени профиль не создаётся,
а сервер возвращает обновлённый preview для повторного подтверждения.
Для ускоренного ввода доступна атомарная форма
`PATCH /api/sessions/:id/task-answers`. Значения `level` и `style` принимаются
в каноническом виде (`beginner|intermediate|expert`, `brief|detailed`);
неизвестные старые текстовые значения не преобразуются автоматически.

Если в новом диалоге выбран профиль «Новый пользователь» и в диалоге ещё не
было задач, анкета стартует автоматически с первым сообщением. После отмены
или при наличии любой предыдущей задачи повторного автостарта нет. Подтверждение
перехода в `done` создаёт профиль из ответов, выбирает его для диалога и добавляет
суффикс ` (2)`, ` (3)` и так далее при совпадении имени.

## HTTP API

| Метод и путь | Тело | Результат |
| --- | --- | --- |
| `POST /api/sessions/:id/task` | `{ "templateId": "dev", "goal": "..." }` | `{ task: TaskSnapshot }` |
| `PATCH /api/sessions/:id/task` | `{ "action": "approve", "pendingTransitionId": "...", "expectedRevision": 1 }` | `{ task: TaskSnapshot }` |
| `PATCH /api/sessions/:id/task-answers` | `{ "answers": { ...5 fields }, "expectedRevision": 0 }` | `{ task: TaskSnapshot }` |

`PATCH` принимает `approve`, `reject`, `pause`, `resume` и `cancel`. Для
`approve`/`reject` нужен `pendingTransitionId` либо legacy `stage`; лишние поля
отклоняются. Ответы
имеют `Cache-Control: no-store`. Неверные данные дают `400`, отсутствующий
диалог или задача — `404`, занятый диалог и отказ автомата — `409`.

## Коды отказов

`TRANSITION_NOT_ALLOWED` содержит `allowedNext`; `ANSWERS_MISSING` содержит
`missing`; `TASK_PAUSED`,
`TASK_FINISHED`, `TRANSITION_PENDING`, `NO_PENDING_TRANSITION` и
`STAGE_MISMATCH` объясняют конфликт с текущим состоянием. Эти же проверки
используются при запросе перехода агентом и при подтверждении пользователем.
