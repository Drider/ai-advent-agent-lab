# Задачи и процессы

В каждом диалоге может быть не более одной незавершённой задачи. Незавершённой считается задача со статусом `active` или `paused`; завершённые (`done`) и отменённые (`cancelled`) остаются в истории диалога и не занимают этот слот. Состояние задачи хранится отдельно от сообщений, памяти проекта и файлов рабочего каталога.

## Три уровня состояния

- Диалог хранит сообщения, ходы, продолжение, task state и историю задач именно этого диалога.
- Проектная память общая для диалогов проекта и является только контекстом. Она не создаёт task, approval или validation.
- Workflow — опубликованная версия процесса, подключённая к конкретной задаче. Его узел, ревизия, артефакты, approvals и validations принадлежат только этой задаче.

Новый обычный вопрос не получает workflow автоматически: он создаёт basic task с одним свободным шагом. Questionnaire, code и analytics подключаются только явным выбором пользователя или выбранным default workflow профиля. В `GET /api/sessions/:id` текущая задача доступна в `taskView`, а все задачи диалога — в `taskHistory`; если задачи нет, `taskView.task` равен `null`.

## Команды

В чате доступны точные команды:

```text
/task pause
/task resume
/task cancel
/task complete
/task attach <workflowId> <version>
/task approve <approvalId>
```

HTTP-команды используют `POST /api/sessions/:id/task-command` и `POST /api/tasks/:id/actions`. Создание задачи — `POST /api/sessions/:id/tasks` с выбором `none`, `profile_default` или конкретной опубликованной версии. Каждая мутация содержит новый `operationId` и ожидаемую ревизию; повтор того же operation ID безопасно возвращает сохранённый результат, а конфликт ревизии отклоняется.

## Проверки и authority

Переход разрешается только из текущего узла, с текущей ревизией и ожидаемым actor. Approval подтверждает пользователь для конкретного immutable-артефакта и node visit. Validation привязана к текущим входам и визиту; старый успешный результат не переносится на изменённый артефакт.

История сообщений, memory, скопированные UI tool parts и экспортированные материалы — данные, а не authority. Они не могут сами создать approval, пройти validation или разрешить переход. Структурные проверки проверяют форму JSON (например, поля plan/answers/implementation); свободный текст результата не доказывает выполнение формальной проверки.

## Анкета, продолжение и экспорт

Анкета добровольна и запускается только после подключения questionnaire. Неполный ответ получает failed validation и возвращает задачу к сбору ответов. Экспортируются только allowlisted-артефакты успешно завершённой задачи, только для новой задачи в том же диалоге. Ветка или другой проект не получают такой экспорт как authority или как новую задачу.

Обычное безопасное продолжение прерванного хода использует старую операцию `continue` и сохраняет legacy-поведение: старый ход без `task_id` продолжится без фиктивной задачи и approval. Продолжение paused task сначала создаётся отдельной командой `/task resume`; сервер выдаёт `resumeRequestId`, который должен принадлежать исходной задаче. Потерянный ответ POST восстанавливается по этому ID, а устаревший ID отклоняется.

## Очистка и ветки

Очистка истории диалога атомарно удаляет его tasks, artifacts, events, commands, approvals, validations, tool operations и task exports. До удаления commands их operation IDs и неиспользованные resume IDs заносятся в `cleared_requests`, поэтому старые запросы нельзя переиспользовать. Очистка блокируется при running turn, незавершённой command/tool operation, `needs_review`, uncertain effect или pending удалении диагностического лога. Самостоятельная project memory и внешние файлы сохраняются; ссылки памяти на очищенные сообщения обнуляются.

Ветка копирует только завершённый префикс conversation context и допустимые context checkpoints/facts. Она не наследует tasks, approvals, validations, exports, authority или незавершённые ходы. Проектная память остаётся общей по правилам проекта, но продолжает считаться контекстом.

## Границы первой версии

Генерация workflow, визуальный граф, drag-and-drop редактор и автоматическое угадывание процесса отложены. Опубликованные JSON/YAML-схемы и версии можно просматривать и подключать; серверный enforcement выполняется независимо от того, отправлена команда из UI, API или модели.
