# Agent Chat

Небольшой потоковый чат на Nuxt 4 и AI SDK. Серверный `ToolLoopAgent` отвечает на обычные вопросы и обязательно использует инструмент для бросков кубика: `d6` по умолчанию, либо любой `dN` от `d2` до `d1000`.

## Запуск

Требования: Node.js 22.18+ и npm.

```bash
npm ci
cp .env.example .env
npm run dev
```

После этого откройте `http://localhost:3000`.

В `.env` укажите OpenAI-совместимый endpoint и ключ:

```dotenv
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_API_KEY=...
LLM_MODEL_DEFAULT=deepseek/deepseek-v4.1-flash
LLM_LOG_LEVEL=basic
```

`LLM_MODEL_DEFAULT` необязателен: тот же ID модели можно изменить в левой панели чата. Ключ читается только сервером и не попадает в браузер.

## Проверка

- обычный вопрос получает потоковый ответ;
- `брось кубик`, `d10` и `d20` вызывают серверный инструмент `rollDie`;
- запросы вроде `покажи сохранённые броски` вызывают инструмент `listSavedRolls`;
- несколько бросков используют отдельные результаты инструмента;
- кнопка «Новая сессия» очищает текущий диалог и возвращает модель по умолчанию;
- обновление страницы не восстанавливает историю: она живёт только в памяти вкладки.

Уровни `LLM_LOG_LEVEL`: `off`, `basic`, `detailed`, `raw`. Записи сохраняются в `data/runs/`, каталог не добавляется в Git.

## Структура инструментов

Все серверные инструменты собраны в [`server/tools/`](server/tools/README.md) и
разделены на функциональные группы:

- [`server/tools/dice`](server/tools/dice/README.md) — `rollDie` и
  `listSavedRolls`, включая CSV-историю бросков;
- [`server/tools/files`](server/tools/files/README.md) — `find_files`,
  `read_file`, `search_text`, `text_stats` и `write_file`.
- [`server/tools/sessions`](server/tools/sessions/README.md) — `list_sessions` и
  `analyze_sessions` для JSON-логов диалогов.

У каждой группы есть `index.ts` как публичная точка входа и README с описанием,
ограничениями и примерами.

Каждый результат `rollDie` сохраняется в локальном файле `data/dice-rolls.csv`. Колонки: `result`, `date`, `time`; дата и время записываются в UTC, время содержит суффикс `Z`. Файл создаётся при первом броске и не добавляется в Git независимо от `LLM_LOG_LEVEL`.

Провайдер должен поддерживать OpenAI-compatible Chat Completions и tool calling. У разных совместимых провайдеров могут отличаться названия моделей, формат метаданных и качество вызова инструментов; при проблемах сначала проверьте поддержку function/tool calling для выбранной модели.

## Файловые инструменты

Рабочая папка агента — `data/`. Она создаётся при первой записи и исключена из Git. Агент принимает только относительные пути внутри этой папки; пути с `..`, абсолютные пути, обратные слеши и симлинки отклоняются.

- `find_files` находит обычные файлы по glob-маске, например `notes/*.md` или `notes/**/*.md`;
- `read_file` читает один UTF-8 текстовый файл;
- `search_text` ищет буквальную чувствительную к регистру подстроку по строкам;
- `text_stats` считает строки, слова и Unicode-символы;
- `write_file` создаёт новый UTF-8 файл и родительские каталоги, но не перезаписывает существующий.

Размер файла или передаваемого текста ограничен 16 КиБ. Поиск возвращает не более 50 путей, поиск строк — не более 100 совпадений, обход — не более 1000 записей. При превышении лимита результат явно помечается ошибкой или флагом `truncated`. Повторная запись возвращает ошибку `ALREADY_EXISTS`.

Пример подготовки данных:

```bash
mkdir -p data/notes
printf 'TODO: первая задача\nГотово\n' > data/notes/a.md
printf 'TODO: вторая задача\n' > data/notes/b.md
```

Примеры запросов в чате:

```text
Найди все файлы notes/*.md и покажи список.
Прочитай notes/a.md и notes/b.md, найди TODO и посчитай статистику.
Собери TODO из notes/*.md и сохрани отчёт в reports/todo.md.
```

Для повторного запуска используйте новое имя отчёта: `write_file` намеренно не перезаписывает существующие файлы. Независимые вызовы инструментов могут выполняться параллельно, а зависимые шаги выполняются после получения предыдущих результатов; конкретная модель или провайдер могут выбирать последовательный вариант.

Текст прочитанных файлов передаётся выбранному LLM-провайдеру. При `LLM_LOG_LEVEL=detailed` или `raw` содержимое и результаты инструментов могут попасть в диагностический лог `data/runs/`.

## Анализ сессий

Агент сам ищет JSON-логи внутри `data/` через `find_files`, читает выбранные файлы через `read_session_file` и передаёт их пути в `analyze_sessions`. Логи из `data/runs/` доступны автоматически. Дополнительные JSON-логи можно разместить в любой папке внутри `data/`.

Для текущего диалога агент использует `get_current_session`: инструмент знает точный `runId`, модель, уровень логирования и путь к файлу, а также показывает уже сохранённые запросы. Запрос, на который агент отвечает прямо сейчас, попадёт в лог только после завершения ответа. Если лог ещё не создан или логирование выключено, инструмент сообщает об этом и всё равно возвращает сведения о текущей сессии.

Примеры запросов:

```text
Покажи доступные сессии.
Что уже сохранено в текущей сессии?
Найди лог за 9 ноября, прочитай его запросы и ошибки.
Сколько запросов и токенов было по дням с 2026-11-01 по 2026-11-10?
Сгруппируй запросы по моделям и покажи суммарные токены.
Какие инструменты вызывались чаще всего?
```

`read_session_file` читает файл до 2 МиБ, возвращает метаданные и страницы по 1–10 запросов; можно искать подстроку в вопросах и ответах. Текст каждого вопроса и ответа ограничен 1000 символами в одном результате. `analyze_sessions` принимает до 20 выбранных путей, группирует по UTC-дню, модели, инструменту или сессии и умеет фильтровать по датам, модели, инструменту и `runId`. В логах уровня `basic` сведения о модели и вызовах инструментов отсутствуют; в таких срезах они обозначаются `(unknown)`. Один запрос с несколькими разными инструментами попадает в каждую соответствующую группу.
