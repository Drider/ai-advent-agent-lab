# Agent Chat

Потоковый чат на Nuxt 4 и AI SDK. Серверный `ToolLoopAgent` отвечает на вопросы, бросает кубик, читает текстовые файлы и PDF, анализирует диагностические сессии. Пользовательская история сохраняется в SQLite: её можно открыть после перезапуска, продолжить после безопасного прерывания и просмотреть вместе с вызовами инструментов.

## Запуск

Требования: Node.js 22.18+ и npm.

```bash
npm ci
cp .env.example .env
```

В `.env` укажите адрес и ключ провайдера, который поддерживает OpenAI-совместимый Chat Completions API и вызовы инструментов:

```dotenv
LLM_BASE_URL=https://openrouter.ai/api/v1
LLM_API_KEY=...
LLM_MODEL_DEFAULT=deepseek/deepseek-v4.1-flash
LLM_LOG_LEVEL=basic
```

Замените пример адреса, ключа и при необходимости ID модели значениями своего провайдера. `LLM_BASE_URL` и `LLM_API_KEY` обязательны; `LLM_MODEL_DEFAULT` и `LLM_LOG_LEVEL` необязательны. ID модели можно изменить в левой панели чата для следующего запроса. Ключ читается только сервером и не попадает в браузер.

Запустите приложение и откройте `http://localhost:3000`:

```bash
npm run dev
```

Для резервной копии работающей базы используйте live-backup API SQLite:

```bash
npm run backup:chat
```

## Что попробовать

- обычный вопрос получает потоковый ответ;
- `брось кубик`, `d10` и `d20` вызывают серверный инструмент `rollDie`;
- запросы вроде `покажи сохранённые броски` вызывают инструмент `listSavedRolls`;
- несколько бросков используют отдельные результаты инструмента;
- запрос `Найди все файлы notes/*.md` вызывает `find_files`, а запрос на отчёт создаёт новый файл через `write_file`;
- вопросы о текущей или прошлых сессиях вызывают инструменты чтения и анализа JSON-логов;
- кнопка «Новая сессия» создаёт отдельный диалог и возвращает модель по умолчанию;
- обновление страницы восстанавливает выбранный диалог из `data/chat.sqlite`;
- прерванный ход показывает действие «Продолжить», а неопределённый побочный эффект переводит его в «Нужна проверка».

Вызовы инструментов показаны компактными строками: нажмите на строку, чтобы увидеть аргументы и результат. Во время ответа можно остановить генерацию, а после ошибки — повторить запрос. Под ответом отображаются число токенов и время генерации.

В шапке чата показан общий расход токенов за диалог — сумма `totalTokens` из доступной статистики всех ответов модели. Счётчик обновляется по мере получения статистики API и восстанавливается из сохранённой истории. Повторная передача истории учитывается при каждом запросе, поэтому общий расход может превышать размер контекстного окна. Ответы без статистики API в сумму не входят.

Уровни `LLM_LOG_LEVEL`: `off`, `basic`, `detailed`, `raw`. Записи сохраняются в `data/runs/`, каталог не добавляется в Git. Уровень `off` отключает только диагностические JSON-логи и не отключает историю чатов.

## Хранение истории и резервные копии

`data/chat.sqlite` — источник пользовательской истории. В базе находятся сессии, полные `UIMessage`, статусы ходов, подтверждённые вызовы инструментов и история бросков кубика. Каталог `data/` исключён из Git и создаётся с ограниченными правами; не публикуйте его содержимое: сообщения и результаты `read_file` могут содержать чувствительные данные.

Схема пути сообщения от браузера до полного ответа и описание записей в базе приведены в [документации по сохранению сессии](docs/chat-session-persistence.md).

Сервер принимает от браузера только новую пользовательскую реплику или явную команду продолжения. История и `run_log_id` загружаются на сервере. `data/runs/run-*.json` остаются отдельными диагностическими логами и могут отсутствовать при `LLM_LOG_LEVEL=off`.

На каждом ходе сервер передаёт модели всю сохранённую историю сессии без собственного ограничения на число сообщений или общий размер контекста. Если история превышает контекстное окно выбранной модели, провайдер может отклонить запрос; автоматическое сжатие истории приложением не выполняется.

Для копии работающей базы запускайте:

```bash
npm run backup:chat
```

По умолчанию скрипт создаёт `data/backups/chat-<ISO>.sqlite`. Для проверки или ручного восстановления можно передать пути:

```bash
node scripts/backup-chat-db.mjs \
  --source /path/to/chat.sqlite \
  --output /path/to/chat-copy.sqlite
```

Скрипт использует SQLite Backup API, а не копирование файла WAL. Для восстановления остановите приложение, сохраните текущую базу и замените `data/chat.sqlite` проверенной копией. После запуска проверьте список диалогов и последние сообщения.

## Структура инструментов

Все серверные инструменты собраны в [`server/tools/`](server/tools/README.md) и
разделены на функциональные группы:

- [`server/tools/dice`](server/tools/dice/README.md) — `rollDie` и
  `listSavedRolls`, включая CSV-историю бросков;
- [`server/tools/files`](server/tools/files/README.md) — `find_files`,
  `read_file`, `read_pdf`, `search_text`, `text_stats` и `write_file`;
- [`server/tools/sessions`](server/tools/sessions/README.md) —
  `get_current_session`, `list_sessions`, `read_session_file` и
  `analyze_sessions` для JSON-логов диалогов.

У каждой группы есть `index.ts` как публичная точка входа и README с описанием,
ограничениями и примерами.

Новые результаты `rollDie` сохраняются в `data/chat.sqlite` с уникальным `tool_call_id`, поэтому повтор того же вызова возвращает прежний результат. Старый `data/dice-rolls.csv` поддерживается для одноразового импорта и экспорта совместимости; новые броски не используют CSV как источник истины.

Провайдер должен поддерживать OpenAI-compatible Chat Completions и tool calling. У разных совместимых провайдеров могут отличаться названия моделей, формат метаданных и качество вызова инструментов; при проблемах сначала проверьте поддержку function/tool calling для выбранной модели.

## Файловые инструменты

Рабочая папка агента — `data/`. Она создаётся при первой записи и исключена из Git. Агент принимает только относительные пути внутри этой папки; пути с `..`, абсолютные пути, обратные слеши и симлинки отклоняются.

- `find_files` находит обычные файлы по glob-маске, например `notes/*.md` или `notes/**/*.md`;
- `read_file` читает один UTF-8 текстовый файл;
- `read_pdf` извлекает текст страницы PDF размером до 20 МиБ;
- `search_text` ищет буквальную чувствительную к регистру подстроку по строкам;
- `text_stats` считает строки, слова и Unicode-символы;
- `write_file` создаёт новый UTF-8 файл и родительские каталоги, но не перезаписывает существующий.

Размер текстового файла или передаваемого текста ограничен 16 КиБ. PDF может занимать до 20 МиБ (20 × 1024 × 1024 байт). `read_pdf` принимает относительный путь, номер страницы (`page`, начиная с 1) и смещение в символах (`offset`). По умолчанию читается первая страница с начала. Один результат содержит до 16 КиБ текста, общее число страниц и `nextOffset`: если он не `null`, следующий вызов читает продолжение той же страницы. Страницы без текстового слоя возвращают пустой текст; OCR не выполняется. Поиск возвращает не более 50 путей, поиск строк — не более 100 совпадений, обход — не более 1000 записей. При превышении лимита результат явно помечается ошибкой или флагом `truncated`. Повторная запись возвращает ошибку `ALREADY_EXISTS`.

Пример подготовки данных:

```bash
mkdir -p data/notes
printf 'TODO: первая задача\nГотово\n' > data/notes/a.md
printf 'TODO: вторая задача\n' > data/notes/b.md
mkdir -p data/documents
cp /путь/к/report.pdf data/documents/report.pdf
```

Примеры запросов в чате:

```text
Найди все файлы notes/*.md и покажи список.
Прочитай notes/a.md и notes/b.md, найди TODO и посчитай статистику.
Собери TODO из notes/*.md и сохрани отчёт в reports/todo.md.
Прочитай PDF documents/report.pdf и кратко перескажи его.
```

Для повторного запуска используйте новое имя отчёта: `write_file` намеренно не перезаписывает существующие файлы. Независимые вызовы инструментов могут выполняться параллельно, а зависимые шаги выполняются после получения предыдущих результатов; конкретная модель или провайдер могут выбирать последовательный вариант.

Текст прочитанных файлов передаётся выбранному LLM-провайдеру. При `LLM_LOG_LEVEL=detailed` или `raw` содержимое и результаты инструментов могут попасть в диагностический лог `data/runs/`.

## Анализ сессий

Агент сам ищет JSON-логи внутри `data/` через `find_files`, читает выбранные файлы через `read_session_file` и передаёт их пути в `analyze_sessions`. Логи из `data/runs/` доступны автоматически. Дополнительные JSON-логи можно разместить в любой папке внутри `data/`.

Для текущего диалога агент использует `get_current_session`: инструмент знает точный `runId`, модель, уровень логирования и путь к файлу, а также показывает уже сохранённые запросы. Запрос, на который агент отвечает прямо сейчас, попадёт в лог только после завершения ответа. Если лог ещё не создан или логирование выключено, инструмент сообщает об этом и всё равно возвращает сведения о текущей сессии.

Примеры запросов:

```text
Покажи доступные сессии.
Что уже сохранено в текущей сессии?
Найди лог за 9 ноября, прочитай его запросы и ошибки.
Сколько запросов и токенов было по дням с 2026-11-01 по 2026-11-10?
Сгруппируй запросы по моделям и покажи суммарные токены.
Какие инструменты вызывались чаще всего?
```

`read_session_file` читает файл до 2 МиБ, возвращает метаданные и страницы по 1–10 запросов; можно искать подстроку в вопросах и ответах. Текст каждого вопроса и ответа ограничен 1000 символами в одном результате. `analyze_sessions` принимает до 20 выбранных путей, группирует по UTC-дню, модели, инструменту или сессии и умеет фильтровать по датам, модели, инструменту и `runId`. В логах уровня `basic` сведения о модели и вызовах инструментов отсутствуют; в таких срезах они обозначаются `(unknown)`. Один запрос с несколькими разными инструментами попадает в каждую соответствующую группу.
